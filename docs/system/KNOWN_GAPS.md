# Известные проблемы (Known Gaps)

Найдено в ходе полного аудита 17.09.2026. **Ничего из этого не исправлено** — по прямому указанию
владельца этот проход был только исследованием и документированием. Приоритет: **P0** (ломает
основной сценарий или целостность данных), **P1** (реальный дефект или риск, заметный
пользователю), **P2** (проблема качества/согласованности), **P3** (косметика/низкое влияние или
превентивная находка).

---

### GAP-001

**Приоритет:** P1
**Область:** Заявки / Почта

**Текущее поведение:** Мониторинг и управление массовой рассылкой (пауза/возобновление/стоп,
предпросмотр продолжения) реализованы только в `frontend/` (старая версия, не используется) — в
`frontend-v2` нет ни маршрута, ни страницы для этого.

**Ожидаемое поведение:** Пользователь может увидеть и управлять запущенной массовой рассылкой из
реально работающего интерфейса.

**Риск:** Запущенную сейчас массовую рассылку невозможно поставить на паузу или остановить из
рабочего интерфейса вообще.

---

### GAP-002

**Приоритет:** P2
**Область:** Поставщики / Процессы

**Текущее поведение:** Служебный маршрут `force_enrich_all_suppliers` (запрошен для этого аудита)
существует только на ветке `state/current-20260917-2119` (git-снапшот этой сессии), не влит в
`experiment/frontend-v2-greenfield-20260905`. Как написан: это **GET**-запрос (должен быть POST —
GET, который тратит бюджет/меняет данные, уязвим к подделке запроса через пассивный `<img>`),
**без проверки CSRF**, **без ограничения частоты запросов**, **без лимита на один вызов** (в
отличие от похожего метода `refresh_bad_global_supplier_names(budget=10)`), и выполняется
синхронно до конца внутри одного HTTP-запроса вместо использования уже существующего устойчивого
пошагового механизма очереди, которым пользуется весь остальной пайплайн обогащения.

**Ожидаемое поведение:** Служебные маршруты, тратящие бюджет платного внешнего API, должны быть
POST-запросами, защищёнными CSRF, с явным лимитом на один вызов.

**Риск:** В худшем случае — `2×N` запросов к Checko за один HTTP-запрос при N поставщиках с уже
известным ИНН, и это будет повторяться при каждом вызове независимо от того, изменилось ли
что-то на самом деле.

### GAP-003

**Приоритет:** **P0**
**Область:** Поставщики

**Текущее поведение:** В таблице `suppliers` может существовать несколько записей одной и той же
реальной компании. Ключ идентичности `(workspace_id, external_key)` незаметно откатывается на
сырой email-адрес, если на момент записи хост неизвестен (`resolve_supplier_for_send`,
`mail/repository.py:3551`) — это не редкий случай: чаще всего происходит, когда сотрудник
компании отвечает с личного адреса (Gmail/Яндекс/Mail.ru), отличного от сайта, который нашёл
поиск.

**Ожидаемое поведение:** Одна реальная компания должна иметь единую каноническую идентичность в
рамках одного рабочего пространства, независимо от того, как именно система впервые её
обнаружила — через поиск по сайту или через личный email в ответном письме.

**Риск:** Переписка и данные обогащения (ИНН, реестр, финансы) могут оказаться привязаны к
разным карточкам одной и той же компании: подтверждено на реальной локальной базе — **28 из 243
строк поставщиков (11.5%)** несут этот признак, из них 12 — именно случай «личный email отличается
от домена компании».

**Статус (19.09.2026, EDW-13/EDW-14/EDW-15 — частично исправлено, Iteration 1 не закрыта):**
- Новая identity для личного email больше не создаётся, если существует **подтверждённая** связь адреса с
  поставщиком: `supplier_identity_evidence` (`migrations/053`, `mail/supplier_identity_evidence.py`) —
  RFQ, отправленный на адрес по карточке (`rfq_sent`), реальный входящий ответ по заголовкам
  (`inbound_reply`), подтверждение пользователя (`manual_confirmed`). Неоднозначность отклоняется, не угадывается.
- Сходство имени ящика с названием сайта — только weak candidate (`name_token_similarity`), сама не связывает.
- Осталось: review path для candidate (EDW-14), обратимый merge/unmerge (EDW-16), миграция 28 исторических дублей (EDW-17).
  До этого отправка на новый личный адрес без evidence всё ещё создаёт отдельную карточку.
- P0 regression `tests/test_supplier_dedup_p0_regression.py` переформулирован как инвариант, а не строковая эвристика.

отправленного письма.

интерфейса.

### GAP-005

**Приоритет:** P2
**Область:** Frontend

**Текущее поведение:** В `frontend-v2` отсутствует единая реализация Input, Checkbox, Card, Table
и Tabs. Поэтому отдельные страницы используют собственные варианты этих элементов, что приводит
к разным размерам, отступам и состояниям. Пример: только для Input — 18+ почти одинаковых
inline-строк Tailwind-классов в 11 разных файлах с мелкими расхождениями (`h-8` вместо `h-9`,
разные внутренние отступы, разные размеры шрифта).

**Ожидаемое поведение:** Для каждого распространённого UI-элемента существует один общий,
переиспользуемый компонент.

**Риск:** Это конкретная, подтверждённая доказательствами первопричина жалобы «выглядит как
франкенштейн» — не всё в интерфейсе несогласованно (Button/Modal/Toast/Badge/состояния
загрузки-пусто-ошибки как раз реально централизованы), но именно эти пять категорий — нет.

**Приоритет:** P2

**Текущее поведение:** Существуют два параллельных способа отображения статус-пилюли:

одновременно, и легко забыть про одно из них.

### GAP-008

**Приоритет:** P2
**Область:** Frontend

**Текущее поведение:** Страница входа (`Login.tsx`) использует прямые цвета Tailwind

### GAP-009

**Приоритет:** P2
**Область:** Frontend

**Текущее поведение:** Библиотека `@tanstack/react-table` подключена как реальная зависимость, но

### GAP-010

**Приоритет:** P1 → **частично закрыт** (см. ниже)
**Область:** QA-инфраструктура

**Текущее поведение (на момент обнаружения 17.09.2026):** У `frontend-v2` было нулевое покрытие
браузерными/e2e/accessibility/визуальными тестами. Всё «тестирование фронтенда» для v2 было
Python-тестами, которые проверяют **текст исходного кода** `.tsx`-файлов, а не реально
отрендеренное и работающее поведение. У `frontend/` (старая версия, не задеплоена) была зрелая
настройка Playwright+axe+Storybook+Applitools, которая так и не была перенесена, когда v2 стал
рабочим интерфейсом.

**Обновление (QA-baseline, коммит этой задачи):** `frontend-v2` теперь имеет собственный
Playwright-контур: `frontend-v2/playwright.config.ts`, `frontend-v2/tests/e2e/` (smoke, axe,
визуальные baseline'ы desktop 1440px и mobile 390px, 2 regression-теста). Реально выполнено и
подтверждено браузером (Chromium) против дискового SAFE_TEST backend (порт 18000, синтетические
данные). Подробности, включая непокрытые части, — в финальном отчёте задачи и
`docs/testing/TEST_CATALOG.yaml` (`TEST-FRONTEND-V2-*`). Storybook для `frontend-v2` **не**
перенесён (см. отчёт: отложено, чтобы не раздувать эту задачу). Оставшийся риск: нет покрытия
Firefox/Safari, нет реальных (не синтетических) сквозных сценариев отправки писем.

**Риск:** Существенно снижен для Chromium/desktop+mobile путей, описанных выше; для всего
остального (другие браузеры, реальная отправка почты) риск не изменился.

### GAP-013

**Приоритет:** P3
**Область:** AI-ассистент

**Текущее поведение:** Ограничение `TOTAL_CONTEXT_CHAR_BUDGET` (40 000 символов) — это грубая
обрезка всей собранной строки контекста с конца, что может обрезать блок самого недавно
добавленного (часто самого важного) поставщика вместо того, чтобы распределять бюджет
пропорционально между поставщиками. У режима «переписка из папки непривязанных писем» вообще нет
ограничения по числу сообщений, только по числу символов на сообщение.

**Ожидаемое поведение:** Ограничение объёма контекста не должно случайно отрезать самые
релевантные данные.

**Риск:** Низкий на практике, но теоретически может ухудшить качество ответа AI-ассистента при
большом количестве выбранных поставщиков/сообщений.

### GAP-015

**Приоритет:** P2
**Область:** Frontend / доступность
**Обнаружено:** автоматизированным axe-прогоном QA-baseline (`frontend-v2/tests/e2e/a11y.spec.ts`)

**Текущее поведение:** На экране входа (`Login.tsx`) элементы `<label>` для полей Email и Пароль
не связаны с соответствующими `<input>` ни через `htmlFor`/`id`, ни через обёртку — axe помечает
это как критическое нарушение (`label`, WCAG 4.1.2/1.3.1). Playwright не может найти поля через
`getByLabel()`; QA-тесты вынужденно используют позиционный селектор
(`form input[type="email"]`) в обход этого.

**Ожидаемое поведение:** Каждое поле формы имеет программно связанную подпись.

**Риск:** Пользователи скринридеров не получают названия полей на экране входа — единственном
экране, доступном без аутентификации.

### GAP-016

**Приоритет:** P2
**Область:** Frontend / адаптивность
**Обнаружено:** мобильным QA-baseline (`frontend-v2/tests/e2e/mobile.spec.ts`, 390px)

**Текущее поведение:** На странице «Заявки» при ширине экрана 390px строка таблицы заявок
присутствует в DOM, но недоступна для клика (не проходит проверку Playwright на
видимость/стабильность) — у таблицы нет мобильной/карточной раскладки.
`document.scrollWidth`/`clientWidth` при этом равны — то есть проблему не ловит проверка на
горизонтальный overflow, только реальное взаимодействие.

**Ожидаемое поведение:** Список заявок остаётся кликабельным на ширине телефона (390px), как и
на планшете/десктопе.

**Риск:** Пользователь на телефоне не может открыть заявку из списка.

### GAP-017

**Приоритет:** P3 (системный технический долг, не блокирует)
**Область:** Frontend / доступность
**Обнаружено:** axe-прогоном QA-baseline на всех проверенных экранах, кроме входа

**Текущее поведение:** Токен `text-ink-muted` на фоне `bg-canvas`/`bg-surface` даёт контраст
≈3.51:1 вместо требуемых 4.5:1 (WCAG AA) — повторяется почти на каждом экране (счётчики,
метаданные, вкладки, состояния загрузки). Намеренно не гейтит QA a11y-тесты (см. комментарий в
`a11y.spec.ts`), иначе технический долг дизайн-системы заблокировал бы весь QA-контур.

**Ожидаемое поведение:** Приглушённый текст соответствует минимальному контрасту AA.

**Риск:** Накопленный, не точечный — требует правки дизайн-токена, а не отдельных компонентов;
явный кандидат для будущего UI-прохода (вне рамок этой QA-задачи).

### GAP-018

**Приоритет:** P2
**Область:** Frontend / доступность
**Обнаружено:** axe-прогоном на `/messages` **после** появления детерминированной фикстуры
переписки (`scripts/seed_qa_fixtures.py`, 2026-09-18) — раньше список переписок был пуст, и
строка с этим багом никогда не рендерилась, поэтому находка была невозможна до заведения
тестовых данных.

**Текущее поведение:** Строка треда в списке переписок — это `<button>` с фокусируемым
элементом внутри (`nested-interactive`, WCAG 4.1.2), например статус-select внутри кликабельной
строки. axe помечает это как `serious`.

**Ожидаемое поведение:** Интерактивные элементы не вкладываются друг в друга — либо строка не
`<button>`, либо вложенный контрол выносится за пределы кликабельной области с остановкой
всплытия клика.

**Риск:** Пользователи скринридеров и клавиатурной навигации получают непредсказуемое поведение
при взаимодействии со строкой переписки — сам факт нового обнаружения демонстрирует, зачем нужна
детерминированная QA-фикстура (`GAP-010`): без данных этот баг был невидим для любого
инструмента.
