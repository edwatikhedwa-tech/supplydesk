# Спецификация экрана Messages (`/messages`, frontend-v2)

Эта спецификация фиксирует постоянные продуктовые правила экрана «Сообщения»
в **frontend-v2** — приложении, которое реально развёрнуто в production
(Vercel `outputDirectory: frontend-v2/dist`). Она описывает, как экран
должен работать, а не что конкретно нужно изменить в текущей задаче.

Правило для любого агента (Claude Code / Codex): **при любой задаче,
затрагивающей экран Messages, сначала прочитать этот файл.** Изменения не
должны нарушать зафиксированные здесь инварианты. Если в ходе работы
принимается новое постоянное решение по Messages, после реализации нужно
обновить этот документ.

`docs/product/messages-workspace.md` описывает **legacy frontend v1**
(другая архитектура, `EmailWorkspace`/`uiContracts.ts` — этого нет в
frontend-v2) и помечен как `SUPERSEDED`. Не использовать его для планирования
работы над frontend-v2.

Этот документ описывает **фактическое текущее поведение кода**. Если
поведение не реализовано — это явно написано как пробел, а не как
предложение сделать это (спецификация не добавляет новые задачи сама по
себе).

## 1. Назначение экрана

`/messages` связывает три сущности в одном рабочем пространстве: **заявку**,
**поставщика** и **переписку**. Это единственное место в продукте, где видна
реальная коммуникация с поставщиком по конкретной заявке.

## 2. Структура рабочего пространства

Основной layout — `react-resizable-panels` `Group` (horizontal):

- **Левая панель** (`Panel defaultSize="30%" minSize="22%" maxSize="42%"`) —
  список заявок и переписок.
- **Правая панель** (`Panel minSize="35%"`) — открытая переписка.
- **Контекстная панель** (не resizable, фиксированная ширина) — одна из:
  `SupplierCardPanel` (кнопка «Заметки»), `TasksPanel` (кнопка «Задачи»),
  `AiChatPanel` (кнопка «ИИ-помощник»). Открыта максимум одна панель
  одновременно (открытие одной закрывает две другие).
- **Иконочный рэйл** (desktop, `!isNarrow`) — вертикальная колонка из трёх
  кнопок (Заметки / Задачи / ИИ-помощник) справа от переписки; отключены,
  пока нет открытой переписки (`!activeThread`).

**Мобильная раскладка** (`useIsNarrowViewport`): список и переписка
показываются по очереди (`mobileView: 'list' | 'conversation'`), контекстные
панели рендерятся как полноэкранный оверлей (`fixed inset-0 z-40`), три
кнопки живут в шапке переписки вместо рэйла.

## 3. Логика заявка → поставщик → коммуникация

- Список слева группирует переписки (`threads`) по `request_id`.
- **Переписка (`mail_thread`) существует только при реальной коммуникации.**
  Backend (`mail/repository.py::list_threads`, предикат
  `_communication_message_predicate`) отдаёт тред только если по нему есть
  хотя бы одно входящее сообщение или исходящее, реально дошедшее до SMTP
  (или подтверждённо не дошедшее — `failed`/`bounced` с зафиксированным
  `irreversible_at`). Просто найденный/сматченный, но ещё не отправленный
  поставщик **не** порождает тред и не появляется в этом списке.
- Группа заявки раскрывается автоматически, если в ней есть непрочитанный
  ответ, либо это запрошенная (deep-link) заявка.
- Заголовок треда открывает переписку через `selectThread`; deep-link
  поддержан через `?thread=`/`?request=&supplier=`.

## 4. Непривязанные письма (unmatched)

- Виджет «Новые письма без заявки за неделю» — непрочитанные, полученные за
  последние 7 дней (`weeklyUnmatched`).
- «Показать остальные без заявки» — всё, что не попало в недельный виджет
  (старое или уже прочитанное), иначе оно нигде не было видно.
- Автоматической привязки по перетаскиванию (drag-and-drop) в frontend-v2
  **нет** (это было в legacy v1). Привязка — только через явные действия:
  подсказка «Похоже на …» (`inboxSuggestions`, только при одном явном
  совпадении) → «Связать с найденной заявкой», либо «Связать вручную»
  (`ManualLinkModal`), либо «Игнорировать» (с подтверждением, необратимо).

## 5. Карточка поставщика

Кнопка **«Заметки»** в контексте открытой переписки открывает
**`SupplierCardPanel`** — контекстную карточку поставщика внутри рабочего
пространства Messages, а не отдельное абстрактное окно заметок и не
навигацию на отдельную страницу. Пользователь остаётся на экране Messages.

`SupplierCardPanel` содержит:

1. **Заметку по этой переписке** (request + request-scoped supplier id) —
   тот же стор, что был у старой отдельной панели заметок
   (`getThreadNote`/`saveThreadNote`), видна независимо от того, подтверждён
   ли поставщик в общем справочнике.
2. Если у треда есть `global_supplier_id` (поставщик подтверждён/привязан к
   общему справочнику) — полную карточку поставщика: контакты и реквизиты,
   график финансов (при ≥2 годах отчётности), показатели (возраст, число
   заявок, выручка, прибыль, отклик, среднее время ответа), заметку о
   поставщике (глобальную, видна по всем его заявкам —
   `saveGlobalSupplierNote`), историю заявок, действия «Написать» /
   «Избранное» / «В чёрный список».
3. Если `global_supplier_id` ещё `null` — заглушка «Карточка появится после
   подтверждения поставщика»; заметка по переписке (п.1) всё равно доступна.

Карточка **не является новой независимой сущностью** — она переиспользует
`SupplierCardContent` (`frontend-v2/src/components/SupplierCardContent.tsx`),
тот же компонент, что рендерит полную страницу `/suppliers/:id`
(`SupplierDetail.tsx`), в компактном (`compact`) режиме с однoколоночной
раскладкой. Панель также даёт ссылку «Открыть полную карточку» на
`/suppliers/:id` для тех, кому нужна страница целиком.

**Инвариант:** если в дальнейшем карточка поставщика в системе меняется —
контекстная панель в Messages обязана использовать тот же компонент, а не
получать собственную отдельную реализацию.

## 6. ИИ-помощник (`AiChatPanel`)

- Открывается кнопкой «ИИ-помощник»; история чата хранится **на сервере**
  (`ai_conversations`/`ai_messages`, `migrations/040_ai_conversations.sql`,
  `mail/ai_conversations.py`) — переживает refresh, закрытие вкладки,
  повторный вход. `localStorage` для истории чата больше не используется.
  Панель при открытии автоматически подгружает самый свежий чат по текущей
  заявке (`GET /api/ai/conversations?request_id=`); для непривязанного
  письма (`inboxMessageId`, нет `request_id`) история не сохраняется —
  каждое открытие начинает новый чат (осознанная граница, нет устойчивого
  ключа группировки для непривязанной переписки).
- «+ Новый чат» / «История» в шапке панели: «Новый чат» очищает
  `conversation_id` и локальные сообщения, не трогая текущий выбор
  поставщиков в чекбоксах слева — выбор контекста и история чата
  независимы (см. §7). «История» показывает список прошлых чатов по этой
  заявке (заголовок — обрезанный первый вопрос пользователя).
- Дневной лимит расхода показывается (`spent_rub`/`limit_rub`), поле ввода
  блокируется при достижении лимита.
- Payload к `/api/ai/chat` — структурированный, не текстовая строка:
  `{conversation_id, request_id, thread_ids, inbox_message_id, message}`.
  Фактический текст, уходящий модели, строится **на backend**
  (`backend/domain/ai_agent/chat_service.py::_build_context`), не на
  frontend — см. §7.

## 7. Правила формирования AI-контекста (кто может попасть в сравнение)

**AI-context invariant, обязательный к соблюдению:** в контекст
ИИ-помощника (и в список доступных для выбора «сиблингов» в панели/
чекбоксах слева) может попасть только поставщик текущей заявки со
статусом **«Есть ответ»** (`threadResponseStatus(t) === 'answered'`, то
есть `replies_count > 0` — та же метка, что показана бейджем в списке
переписок). Это строже, чем просто «было отправлено письмо»: заявка может
иметь 100+ переписок, по которым письмо ушло, но ответил только десяток —
в сравнение («кто дал самую низкую цену?») годятся только те, у кого
реально есть что сравнивать. Поставщик со статусом «Не отправлено»,
«Ожидаем ответ» (отправлено, ответа ещё нет), «Ошибка» или просто
найденный/сматченный без отправки — **не должен** появляться как источник
контекста для ИИ.

**С 2026-09-11 реальная граница безопасности/корректности — на backend, не
на frontend.** Раньше (до `TASK-MESSAGES-LINKS-STATUS-SEND-AI-20260910`)
frontend отправлял готовую текстовую строку, backend её слепо
конкатенировал в промпт без какой-либо проверки. Теперь:

1. Frontend (`frontend-v2/src/pages/Messages.tsx`, `aiContextThreadIds`)
   по-прежнему фильтрует чекбоксы/«Выбрать всех» по
   `threadResponseStatus(t) === 'answered'` — это UX-слой, не безопасность.
2. Backend (`AiChatService._build_context`) для каждого присланного
   `thread_id` проверяет через `MailRepository.get_thread_owned(workspace_id,
   request_id, thread_id)`, что тред реально принадлежит текущему
   workspace **и** текущей заявке — иначе id молча отбрасывается, ни при
   каких обстоятельствах не попадая в промпт. Backend **сам** заново
   читает реальные сообщения из БД (`thread_messages`) для каждого
   подтверждённого треда — тексту, присланному frontend, больше не
   доверяет вообще ничего, кроме списка id.
3. Контекст строится по структуре «ЗАЯВКА → блок ПОСТАВЩИК на каждого
   выбранного → сообщения с ролью (Мы/Поставщик) и датой» — явно
   разграничен по поставщикам, не единая склеенная строка. Бюджет на
   сообщение — `PER_MESSAGE_CHAR_LIMIT` (см. код, обрезка сохраняет и
   начало, и конец сообщения, т.к. контактная подпись поставщика часто в
   конце) и общий `TOTAL_CONTEXT_CHAR_BUDGET`.
4. `context_thread_ids` каждого пользовательского сообщения сохраняется в
   `ai_messages` как аудиторский след — какие именно переписки реально
   вошли в конкретный ответ ИИ.

Backend-тест: `tests/test_ai_context_scoping.py` — 132 реальных поставщика
в одной заявке, выбраны 3, подтверждено (через настоящий
`AiChatService.send_message` с подставным LLM-клиентом, фиксирующим точный
промпт): в тексте, отправленном модели, ровно 3 блока `ПОСТАВЩИК:`, только
выбранные имена, ни одного из оставшихся 129; отдельные тесты проверяют,
что id чужой заявки/чужого workspace молча отбрасывается. Живая проверка
(браузер, реальные данные, заявка «Печь-камин — глубокий поиск 20», 132
переписки/26 «Есть ответ») подтвердила то же самое на настоящем `/api/ai/chat`.

- Кнопка **«Выбрать всех поставщиков по заявке»** выбирает
  `siblingThreads.map(t => t.id)` — то есть всех поставщиков **текущей
  заявки со статусом «Есть ответ»**, а не вообще всех поставщиков заявки и
  не всех, кому просто отправлено письмо.
- Выбор (`aiExtraThreadIds`) переживает переключение между тредами **одной и
  той же** заявки (открыть ответ другого уже выбранного поставщика — обычный
  шаг сравнения, не должен сбрасывать выбор). Переключение на тред **другой**
  заявки — новый контекст, выбор сбрасывается (`useEffect` на
  `activeThread?.request_id`, не на `activeThread?.id`).
- Активный (открытый) тред исключается из списка «дополнительных» контекстов,
  даже если он остался в `aiExtraThreadIds` после такого переключения — иначе
  его переписка ушла бы модели дважды.

## 8. Отображение выбранных поставщиков (layout-инвариант)

Список выбранных поставщиков в `AiChatPanel` — сворачиваемый аккордеон
(«Контекст: N поставщиков», склонение по правилам русского языка), свёрнут
по умолчанию. Разворачивается по клику, список внутри ограничен `max-h-40` с
собственным independent scroll.

**Инвариант:** поле ввода вопроса и кнопка «Отправить» должны оставаться
видимыми и достижимыми независимо от того, сколько поставщиков выбрано —
хоть 2, хоть 100+. Раскрытый список выбранных не должен растягивать всю
панель. Проверено вручную на живых данных с 2 и со 126 выбранными
поставщиками (см. `ai/reports/` соответствующей задачи) — оба случая
работают корректно.

## 9. Отображение содержимого писем

Тело письма рендерится через `EmailRenderer`
(`frontend-v2/src/components/EmailRenderer.tsx`, портирован из
`frontend/src/components/mail/EmailRenderer.tsx`) — сандбоксированный
`<iframe sandbox="allow-same-origin allow-popups allow-popups-to-escape-sandbox">`
с собственным `srcDoc`. Backend уже отдаёт санитизированный `body_html`
(`mail/content.py::sanitize_email_html`, nh3-allowlist: `http`/`https`/
`mailto`/`tel`, без `javascript:`, `target="_blank" rel="noopener noreferrer nofollow"`
на каждой ссылке) и флаг `has_remote_images` — компонент их не пересанитизирует,
только рендерит. Если `body_html` пуст, используется `body_text` с
автоматическим превращением голых URL/`mailto:`/`tel:` в ссылки
(`autolinkPlainText`). Удалённые изображения по умолчанию заблокированы
(`data-remote-src`), с уведомлением в UI. Длинные ссылки/таблицы не ломают
горизонтальную раскладку (`clampEmailMinimumWidths`).

**Инвариант:** любое изменение sanitizer-allowlist остаётся исключительно
backend-стороной (`mail/content.py`); frontend-рендерер не добавляет
собственную логику санитизации HTML.

## 10. Метаданные закупщика («Важное» / приоритет)

Backend (`ThreadSummary.is_important`, `ThreadSummary.priority`) и API это
поддерживают, но **UI frontend-v2 их сейчас нигде не показывает и не
редактирует** — в legacy v1 такой флаг был, в v2 он не перенесён. Это
известный пробел, не текущая функциональность.

## 11. Поиск

На самом экране Messages своей строки поиска нет. Поиск по заявке,
поставщику, теме и тексту письма выполняется через глобальную командную
палитру (⌘K, `search_messages`) и приводит на Messages по deep-link
(`?highlight=<message_id>&q=<query>`), где совпадение подсвечивается
(`highlightText`) и страница скроллится к найденному сообщению.

## 12. Responsive / layout-инварианты

- `useIsNarrowViewport` переключает список/переписку на мобильном в
  последовательный режим (`mobileView`), с кнопкой «Ко всем перепискам».
- Контекстные панели — `fixed inset-0 z-40` на мобильном (оверлей на весь
  экран), обычный flex-сосед с фиксированной шириной на `sm:` и шире
  (`SupplierCardPanel` — `sm:w-[380px]`, `TasksPanel`/старая `NotesPanel` —
  `sm:w-72`, `AiChatPanel` — `sm:w-[340px]`).
- Иконочный рэйл (Заметки/Задачи/ИИ-помощник) рендерится только на
  `!isNarrow` — на мобильном те же три действия живут в шапке переписки.
- Горизонтальный скролл на всей странице не допускается; широкий контент
  (длинные адреса, названия) обрезается (`truncate`) с полным значением в
  `title`/tooltip.

## 13. Пользовательский статус переписки с поставщиком (`conversation_status`)

Отдельно от статуса доставки письма (§ выше, `threadResponseStatus`
— «Есть ответ»/«Ждём ответа»/«Не отправлено») и отдельно от чёрного
списка (`blacklist_entries`, workspace-wide, влияет на реальную отправку)
существует **рабочий статус переписки** — «В работе» / «Отложено» /
«Отклонено», привязан к паре (заявка, поставщик) на пользователя
(`mail_thread_status`, `migrations/039_thread_conversation_status.sql`,
`mail/thread_metadata.py::set_thread_status`/`list_thread_statuses`).
`POST /api/requests/{request_id}/suppliers/{supplier_id}/status`.

- Управляется прямо в списке переписок (компактный `<select>` рядом с
  каждой строкой) и в шапке открытой переписки.
- Список по умолчанию отсортирован: В работе → без статуса → Отложено,
  внутри каждой группы — по давности последнего сообщения.
- «Отклонено» скрывает переписку из основных фильтров (`Все`, `Есть
  ответ`, `Ждём ответа`, `Непрочитанные`), но **не удаляет данные** —
  отдельный фильтр-вкладка «Отклонённые» показывает их снова, оттуда же
  можно вернуть статус на «В работе».
- Никогда не пишет в `blacklist_entries` и не влияет на возможность
  отправки письма этому поставщику.

## 14. Границы (что этот экран намеренно не делает)

- Не имеет собственного глобального редизайна помимо утверждённой
  дизайн-системы (`docs/ui-design-system.md`).
- Не добавляет OCR, автоматический скоринг или логистику поверх переписки —
  логистика доступна отдельной кнопкой «Доставка» → `LogisticsQuoteModal`,
  это не часть содержимого письма.
- MagicRings/страница логина — отдельный, не связанный с Messages, инвариант
  (`ai/DECISIONS.md`, DECISION-020); упомянут здесь только чтобы явно
  исключить путаницу — Messages его не затрагивает.
