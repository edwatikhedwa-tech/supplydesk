# Real mailbox end-to-end integration benchmark (EDW-31)

**Это не оценка качества на реальных поставщиках.** Оба ящика — ваши: A = `edwatik@yandex.ru` (покупатель, подключён к SupplyDesk), B = `edwatik@mail.ru` («поставщик»). Письма уходили только между ними (в коде жёсткая проверка адресов). Содержимое — синтетическое (фикстуры из synthetic extraction benchmark). Реальный supplier benchmark остаётся отдельным будущим gate.

Путь: `A → production send path (queue_one → claim_job → send_claimed_job) → реальный провайдер → B`, затем `B → реальный SMTP mail.ru → A → production sync_incoming (реальный IMAP) → routing → вложения → AI → validation → факты → привязка к заявке`. Письма в БД напрямую не вставлялись.

## Условия и раскрытие обходов
- Работа на **копии** live-БД (`tmp/e2e/`), live-БД и `.env` не менялись.
- Аварийный выключатель `MAIL_OUTGOING_DISABLED` снят **только в переменных окружения тестового процесса**, durable-выключатель включён **только в копии**, runtime-gate («runtime не инициализирован») снят передачей пустого `SUPPLYDESK_ENV` в тестовом процессе — каждое по вашему разрешению. Отправка B→A шла напрямую через провайдер mail.ru (так пишет поставщик), а не через очередь SupplyDesk.
- Ожидаемые результаты 20 сценариев зафиксированы до первой отправки (коммит `f613dc5`, `benchmarks/e2e_mail/scenarios.py`) и не менялись.
- Вложения из «Поставщика» — уже замороженные фикстуры synthetic benchmark.
- В процессе я по ошибке вывел в консоль зашифрованное (не открытое) значение пароля приложения Mail.ru из БД; ключа расшифровки в выводе не было.

## Что построено в production-коде (флаг `MAIL_INTELLIGENCE_ON_SYNC=1`, по умолчанию выключен)
Раньше sync **не сохранял вложения вообще**. Теперь: парсер забирает файлы (≤10 файлов, ≤10 МБ каждый, ≤20 МБ всего), импорт кладёт их в `mail_attachments`, анализ вложений идемпотентен по sha256 (миграция 058: `mail_attachment_analyses`, `mail_attachment_facts`, `mail_attachment_ai_calls`), факты хранят место в файле, стоимость и задержка пишутся.

## Результат по 20 сценариям
| проход | что | пройдено |
|---|---|---|
| 1 | код до правок E2E | **10 из 20** |
| 2 | + два исправления, найденные E2E (тема ответа, копия своего письма) | 11 из 20 |
| 3 | + письмо с вложением без цены в тексте не идёт в модель | **17 из 20** |

Повторная обработка без повторной отправки: проходы 2–3 — пересчёт под новой версией анализа на тех же письмах. Итоговые 17/20 — на исправленном коде, не на первом.

Что показал первый проход (реальные дефекты, не подгонка):
1. **Тема нашего же запроса** («Запрос цены …») в ответе поставщика считалась сигналом цены → 1 платный вызов на письмо «спасибо, принято» и ложный manual review. Исправлено: сигнал ищется только в собственном тексте письма.
2. **Письма с вложением и без цены в тексте** («КП в файле», «расчёт в таблице») тоже уходили в модель. Исправлено: вложение несёт предложение, тело не извлекается.
3. **Двойной объект:** синк ящика B принёс письма A→B (запросы RFQ) как «неразобранные» с тем же Message-ID → два объекта одного сообщения и два лишних AI-анализа собственных писем. Исправлено: входящая копия собственного исходящего письма workspace пропускается. Проверено на реальном IMAP: `rfq_objects = 2` (ожидалось 2), синк B — `skipped 2`.

Осталось не пройдено (ожидания не менялись):
- **S02** «готовим предложение, вернёмся с ценой» (без заголовков ответа, с `[SD-n]` в теме): привязка правилами по маркеру **работает**, но модель вызвана 1 раз (ожидалось 0 — слова «предложение/цена» в тексте).
- **S13** пересланное письмо без маркера: правильно на ручной проверке и не привязано, но 1 вызов модели из-за слова «предложение».
- **S11** неоднозначная заявка: письмо **не привязано** и на ревью (верно), но факт «500 руб.» извлечён и сохранён как proposed без заявки (ожидалось «фактов нет»). Решение по политике: извлекать ли факты до привязки.

## Сквозные проверки
| проверка | результат |
|---|---|
| письмо реально отправлено и получено вторым ящиком | 20/20 (SMTP mail.ru ≈1,1 с на письмо; в IMAP ящика A все 20 с первой попытки) |
| импортировано ровно один раз | 20/20 (по 1 строке на Message-ID) |
| повторный sync A не создаёт дубль | да: `imported 0, skipped 1`, счётчики не изменились |
| повторный анализ без AI | 0 вызовов модели и 0 вызовов вложений при повторе той же версии |
| thread по заголовкам / по маркеру / вручную | thread — 16 писем; маркер `[SD-n]` без заголовков — 1 (S02); неразобранные → ревью — 3 (S11, S13, S19) |
| вложения обработаны, факты, provenance | S06–S09, S14–S16: все цены из файлов извлечены, локатор (лист/строка, таблица/строка, страница/бокс) у 100% фактов, чужих цифр (итоги, реквизиты) нет |
| одинаковый файл: повтор / другое имя | S14, S16: `reused_from` есть, 0 AI, 0 OCR; тот же файл с другим содержимым (S15): новый анализ |
| стоимость и задержка записаны | да: у каждого вызова модели; вложений (текстовые форматы) — 0 ₽, ≈20 мс |
| двойной объект при синке второго ящика | проход 1 — **провал** (2 лишних объекта), после исправления — 0 |

Стоимость всех проходов: 46 вызовов, **0,060 ₽** (лимит 1 ₽), 20,5 тыс. входных и 5,4 тыс. выходных токенов; средняя задержка вызова 6,8 с, максимум 24,8 с. Один проход по 24 письмам синхронно занял 123 с.

## Synthetic extraction benchmark vs real mailbox E2E
| | synthetic extraction | real mailbox E2E |
|---|---|---|
| что доказывает | качество чтения файлов (60 файлов, сканы, OCR, привязка к позициям) | что путь провайдер → sync → routing → вложения → AI → факты работает и идемпотентен |
| ограничения | синтетика, PDF собственного генератора | синтетический контент, два своих ящика, один провайдер-пара, тестовая копия БД |
| не доказывает | реальные файлы поставщиков | качество на письмах реальных поставщиков (будущий gate) |

## Готов ли pipeline к ограниченному включению под feature flag
**Технически — да, для ограниченного включения (один workspace, флаг по умолчанию выключен), при условиях:**
1. Выполнять анализ **из очереди**, не внутри sync (123 с на 24 письма, задержка модели до 25 с).
2. Прогнать миграцию 058 через PostgreSQL gate (`scripts/pg_gate.py`) — на PG не проверялась.
3. Оставить включённым бюджет `MAIL_ANALYSIS_DAILY_BUDGET_RUB` и ревью-очередь; факты — только `proposed`.
4. Принять решения по S02/S11/S13 (политика факта до привязки, слова «предложение» без цены).
5. Переносимый OCR (EDW-34) нужен, если включать сканы на Linux; для xlsx/docx/text-PDF не нужен.
6. Проверить sync_sent ящика B (в E2E не гонялся) на тот же класс «двойной объект».

Не готово / не доказано: работа с реальными файлами и письмами поставщиков (EDW-36 и отдельный supplier benchmark), сканы через провайдера-почту (в E2E не отправлялись), Yandex-исходящие от B (только mail.ru → yandex).
