# Mail Intelligence Core — benchmark на реальных вызовах RouterAI (EDW-26)

Что это: 64 **синтетических** письма (не реальная переписка; реальный ящик не читался и наружу не отправлялся), ожидаемый результат
для каждого написан вручную и закоммичен **до** первого запуска (`benchmarks/mail_analysis/dataset.py`, коммит `9477831`).
Ответы модели истиной не считались; вторая модель (`deepseek/deepseek-v4-flash`) работала только судьёй расхождений.
Модели: cheap `mistralai/mistral-nemo`, strong `openai/gpt-4.1-mini`. Ключ читается из `.env`, в отчёты не попадает.
Стоимость — фактическая, из ответа шлюза (`usage.cost`, `cost_source = provider_reported` в 43/43 AI-запусков).
Запуск: `python benchmarks/mail_analysis/run_benchmark.py --tag <t>`; таблицы: `python benchmarks/mail_analysis/report.py <t>`
(результаты в `results/`, не в git).

## Ошибки по типам (не сведены в одну цифру)
- **Классификация:** 52/58 строго, 6 расхождений — см. выше.
- **Привязка к заявке:** 58/58 (точная по треду, по `[SD-N]`+известный отправитель; сомнительные — кандидаты/ревью, молча ничего не привязано).
- **Обнаружение КП:** TP 28, FP 0, FN 0.
- **Цена:** TP 35, FP 0, FN 0 (в т.ч. ступени цены, несколько позиций, USD/EUR).
- **SKU:** TP 15, FP 4, FN 2. Все 4 «FP» — обозначения, реально присутствующие в тексте: `6205` (в письме «подшипник … 6205», в разметке SKU не было — вопрос разметки, дважды) и `6306-2Z HRB` (бренд приклеен к артикулу, дважды). Выдуманных SKU нет (валидатор проверяет наличие в тексте).

## Каскад и стоимость (v3)
- Без AI 21 (33%), cheap 39, strong 4 (**escalation rate 9,3% от AI-писем**; оправданных 2 — cheap ошибся, strong исправил; 1 лишняя — cheap был прав, валидатор строже; 1 не помогла), manual 8 (5 из них — неоднозначная привязка, по замыслу).
- Ср. стоимость AI-письма: cheap **0,0012 ₽**, с strong **0,044 ₽** (в 35 раз дороже).
- На полученное письмо (при этом миксе): **0,0035 ₽**; на AI-письмо 0,0052 ₽; на полезный результат 0,0080 ₽ (28 КП).
- Прогноз при этом миксе: **1 000 писем ≈ 3,5 ₽, 10 000 ≈ 35 ₽** (все письма через AI: 5,2 ₽ / 52 ₽). Реальный ящик за последние 30 дней: 130 входящих → **≈ 0,46–0,68 ₽ в месяц на workspace**.
- Задержка cheap: p50 5,5 с, p90 7,7 с, макс 11,7 с; между прогонами тот же запрос шёл 0,7–24 с — шлюз маршрутизирует на разные endpoint (DekaLLM, DeepInfra, Parasail), задержка непредсказуема → анализ обязан быть асинхронным.
- Structured output: после strict-схемы 0 платных повторов внутри вызова (`retries_total = 0`), cached tokens 0.

## Идемпотентность на живом API
Повторный запуск pipeline по всем 64 письмам: **0 новых вызовов, 0 ₽**. Повторный sync (48 писем): 0 импортировано, 48 отброшено как дубликаты. «Повторный вход» (новый процесс на той же БД): 0 вызовов. Новая
`analysis_version` без `reprocess`: 0 вызовов. Явный `reprocess` 3 писем: 3 вызова, 0,0043 ₽ (осознанно, версионировано, старые факты `superseded`).

## Проверка validation
Модель не может превратить догадку в факт (тесты `tests/test_mail_analysis_validation.py`, реальные ловушки K01–K06, J04, J05): выдуманные SKU и цена отбрасываются; неверная/невидимая валюта — отклоняется; цитата не из письма — отклоняется;
цена только в цитируемой истории — вырезается до модели; число не-цена (телефон, ИНН, артикул печи) — отклоняется; диапазон цен — отклоняется; «цена за 100 шт» пересчитанная моделью — отклоняется (manual). Две возможные заявки — кандидаты, без привязки.
Неоднозначные письма: `ambiguous_request_link` (5/5 ушли на ревью и не запустили downstream), `supplier_unconfirmed` (заявка известна по `[SD-N]`, поставщик — нет).

## Решение
- **Оставить как есть:** правила «без AI» (33% писем), идемпотентность, ledger, provider-reported cost, cheap-модель nemo как рабочая (без потерь цены/КП на этом наборе), validator.
- **Prompt слабый:** граница `other`/`question` не определена; SKU-границы (бренд в артикуле, голое «6205»).
- **Validation:** был слишком слабый (цена не сверялась с цитатой, валюта, диапазон) — исправлен; был слишком «шумный» (цена без валюты отправляла на strong) — исправлено (`letter_lacks_information`). Осталось: расхождение validator vs ручная разметка по `strong_unnecessary` 1 из 4.
- **Candidate retrieval:** сейчас только адрес отправителя (`suggest_requests_for_inbox`); скоринг по SKU/позициям/теме нужен (EDW-28), прежде чем разрешать LLM выбирать заявку.
- **Strong нужна редко:** 9% AI-писем, в основном многопозиционные КП и ступени цены; не «по умолчанию».
- **Ограничения этого benchmark:** синтетические письма, один cheap-кандидат (без сравнения моделей), без вложений/PDF, без английских/шумных подписей и HTML-мусора реальной почты, 6 спорных писем исключены из метрик.
- **Можно ли закрывать Core:** механика и экономика доказаны; **Iteration 2 закрывать рано** — нужна короткая итерация 2.3: подключение под флагом к живому приёму (асинхронно), валидация на ограниченной выборке реальных писем (с согласия: данные уходят внешнему провайдеру, требуется RouterAI data audit из Pack), решение по таксономии `question`/`other`.
