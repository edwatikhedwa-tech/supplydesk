# SupplyDesk UI audit — 2026-09-04

## Цель и режим

Режим: `REDESIGN` — системное улучшение существующего интерфейса с сохранением
архитектуры, backend-контрактов и бизнес-функций.

Пользователь: специалист по снабжению. Основная работа — быстро найти заявку,
проверить состояние ответа поставщика и выполнить следующее безопасное действие.
Для мобильного сценария приоритет такой же: открыть новое письмо, понять его
связь с заявкой и перейти к ответу/привязке без горизонтальной прокрутки.

## Реально используемые экраны и состояния

- `/` — дашборд: KPI, письма без привязки, последние заявки, ошибки и пустые

  metadata controls, manual link, reply, delivery-unknown recovery.
- `/suppliers` — большой список компаний: фильтры, поиск, selection, registry

  attachments and save feedback.
- `/requests/new`, `/requests/:id`, `/mail/campaigns/:id` — рабочие формы,
  details and campaign/send flows; visual modernization deferred after the
  representative `/messages` slice.

## Найденные системные проблемы

### P1 — иерархия действий

Одинаковые действия имеют разные inline-классы: от `bg-accent-600` до серых
ghost-like кнопок и текстовых ссылок. Пользователь не получает стабильный ответ,
какое действие главное, а какое вторичное.

### P1 — нет общего слоя компонентов

Кнопки, inputs, status pills, counters и empty states повторяются в страницах и
mail-компонентах. Это создаёт визуальный дрейф по высоте, radius, focus ring,
цветам и отступам.

### P1 — `/messages` перегружен служебными сигналами

В одной зоне одновременно находятся tabs, фильтры, яркие counters, статусы,
flag/priority и unmatched preview. Часть counters выглядит как status badges,
хотя количество не описывает состояние.

### P2 — surface noise

Слишком много границ, rounded cards и локальных теней. В списке компании и
переписки рамка часто повторяет саму группировку, вместо того чтобы помогать
сканированию.

### P2 — разные page shells

Дашборд и страницы данных используют разные ширины, плотность и композицию.
`Layout` уже задаёт общую навигацию, но content shell и toolbar patterns не
унифицированы.

### P2 — responsive evidence gap (закрыт автоматизированно, ограничен в CUA)

После изменения полный Playwright-прогон на текущем Vite-render проверил 88/88
сценариев на desktop, tablet и mobile профилях, включая проверку переполнения и
axe accessibility. Встроенный CUA-браузер отдельно дал живой render 1280×720;
он не сохраняет именованный viewport-профиль, поэтому matched CUA screenshot
матрица остаётся ограниченной этим размером.

### P3 — типографическая дисциплина

В проекте есть хорошие page-title tokens, но рядом живут произвольные `text-xs`,
`text-sm`, `text-[10px]`, разные tracking и weight для одинаковых ролей.

`RESOLVED FOR SCREEN TITLES` в задаче
`TASK-SUPPLYDESK-TYPOGRAPHY-SHIMMER-20260904`: глобальный UI font stack теперь
начинается с `Public Sans`/`Geist` и имеет локальные системные fallback-ы;
экранные `h1` используют единые `page-title`/`display-title` размеры и
`sd-shimmer-heading`. Произвольные мелкие domain-метки и встроенный HTML писем
намеренно не переписывались, так как у них другие семантические роли.

## Дубли и инвентарь компонентов

- Buttons: множество inline-реализаций; общего `Button` нет.
- Status: `STATUS_BADGE`, `DeliveryBadge`, `RelationshipBadge`, mail thread
  status и локальные `<span>` с похожими цветами.
- Counters: `rounded-full` badges в dashboard, supplier filters, thread filters,
  unmatched preview и outbox.
- Inputs: повторяющиеся search fields в `Messages`, `ListToolbar`, `Suppliers`,
  `Blacklist`, modal flows.
- Layout: `Layout` общий, но отдельные страницы повторяют `min-h-screen`,
  `max-w-[1600px]`, padding и card shell.
- Empty/error: повторяются icon + text + retry without shared surface semantics.

## Дизайн-направление

SupplyDesk должен выглядеть как рабочий procurement desk: спокойный светлый
canvas, графитовая навигация, один синий action color, тонкие разделители и
сильная типографическая ось. Отличительный элемент — «рабочий стол решения»:
заявка и поставщик читаются как контекст, письмо — как основной объект, а
служебные статусы и количества уходят на второй план.

Принципы:

1. Один визуальный язык для shell, списков и деталей.
2. Primary action — одна синяя кнопка; secondary — нейтральная outlined;
   ghost — только для редких/контекстных действий.
3. Status badge отвечает только на вопрос «что происходит?».
4. Counters — спокойный текстовый metadata, не яркие chips.
5. Группировка строится от объекта данных, а не от количества карточек.
6. Радиусы и spacing используют существующую шкалу 4/8/12/16/24/32.
7. На mobile сохраняются title, sender, subject, status, relation и reply/link;
   широкая split-view превращается в list → detail.
