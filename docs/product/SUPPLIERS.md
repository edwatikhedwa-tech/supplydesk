# Поставщики — идентичность, обогащение и проблема дублирования

Полная модель (трёхуровневая идентичность, граф доказательств, срок актуальности, изоляция
рабочих пространств) уже подробно описана и подтверждена как актуальная в
[`../domain/SUPPLIER_MODEL.md`](../domain/SUPPLIER_MODEL.md) — не дублируется здесь. Этот
документ добавляет то, чего тот документ ещё не покрывает: конкретный, живой дефект
дублирования поставщиков, найденный в ходе этого аудита и проверенный на реальной локальной базе
данных.

## Текущее поведение: как определяется ключ идентичности записи `suppliers`

`upsert_supplier` (`mail/repository.py:3363`) использует ключ `(workspace_id, external_key)`
через `ON CONFLICT DO UPDATE`. `external_key` обычно — это хост, найденный поиском. Но
`resolve_supplier_for_send` — резолвер, определяющий получателя в момент отправки письма —
откатывается, когда хост/`external_key` неизвестны, на:

```python
normalized_key = str(external_key or normalized_host or normalized_email).strip().lower()
```

То есть незаметно использует **сырой email-адрес** как ключ идентичности. Это не редкий
пограничный случай: срабатывает каждый раз, когда покупатель отправляет письмо (или приходит
ответ) на адрес, который отличается от того, что поиск изначально нашёл для этой компании —
чаще всего личный адрес Gmail/Яндекс/Mail.ru реального сотрудника вместо собственного домена
компании.

`resolve_supplier_for_send` действительно сначала пытается найти совпадение по email
(`WHERE LOWER(s.email)=?`), прежде чем откатиться на совпадение по хосту, а затем на создание
новой записи — но это помогает, только если у **уже существующей** записи поле `email` уже
заполнено именно этим адресом. Поставщик, созданный через поиск (`upsert_search_result`),
изначально имеет `email=""`. Поэтому самая первая ручная отправка на личный адрес, найденный на
сайте этого же поставщика, сегодня всё равно создаёт дубликат — эта защита (добавлена коммитом
`85fb7a2d`) закрывает дверь только после того, как через неё уже прошли один раз.

## Подтверждённый масштаб (локальная база данных, 17.09.2026)

| Показатель | Значение |
|---|---|
| Всего строк в `suppliers` | 243 |
| Строк, где `external_key == email` (признак этой проблемы) | 28 (11.5%) |
| Из них адрес ответа — личная почта (Gmail/Яндекс/Mail.ru и т.п.) | 12 |

Изначально сообщённый случай (заявка №1059, `sfera.termo@yandex.ru`) — один из примеров этого
паттерна: поставщик с id 2837 (`external_key=termo-sfera.pro`, есть реальные данные реестра и
финансов) и поставщик с id 3315 (`external_key` равен самому email-адресу, держит реальную
переписку) — это две записи для одной реальной компании. Запись 3315 была создана **исходящей**
отправкой без указанного хоста (`request_suppliers.reason='Добавлен при отправке письма.'`), а
не обработкой входящего ответа — путь входящих писем (`import_incoming_messages`) никогда не
создаёт запись поставщика; он только помещает непривязанное письмо в очередь или присоединяет
его к *уже существующему* поставщику.

## Ограничения на сохранение данных при будущем исправлении

Проверено для этой конкретной пары: у `tasks`, `mail_thread_notes`,
`workspace_supplier_contacts`, `blacklist_entries` — **ноль строк**, привязанных к любому из двух
id — объединение здесь ничего бы не потеряло. Запись 3315 единолично держит живые `mail_threads`/
`mail_messages`/`request_supplier_states`; запись 2837 единолично держит данные позиций из
поиска в `supplier_profiles`/`request_suppliers`. Правильное исправление должно перенаправить
данные почтовой стороны на обогащённую карточку (или наоборот), не потеряв ни одну из сторон —
и должно делать это универсально, поскольку у других пар из этих 28 могут быть заметки/задачи/
переопределения контактов, которых нет именно в этой паре.

## Ожидаемое поведение (согласно заявленному инварианту)

`docs/domain/SUPPLIER_MODEL.md` §2: «поставщик — каноническая сущность; одна организация не
должна заново создаваться... ни внутри одного workspace». Один и тот же реальный
контрагент никогда не должен занимать две записи `suppliers` в рамках одного рабочего
пространства только потому, что один раз он был найден по хосту, а другой раз — по личному
адресу ответа.
