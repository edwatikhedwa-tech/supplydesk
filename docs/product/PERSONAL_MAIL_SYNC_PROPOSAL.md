# Внешняя почта и автоматическая связь писем с заявками

## Цель

SupplyDesk не заменяет привычный почтовый клиент. Снабженец может создать
заявку в SupplyDesk, написать поставщику из Gmail, Яндекс.Почты, Mail.ru или
корпоративного ящика и затем увидеть эту переписку в заявке после
синхронизации. Главный поток: `внешнее письмо → поставщик → заявка → история`.

## Факты текущей реализации

Аудит исходного кода от 2026-09-12 подтвердил следующее.

| Область | Сейчас | Последствие |
| --- | --- | --- |
| Yandex и Mail.ru | Оба адаптера читают IMAP-папку `INBOX` в read-only режиме. Mail.ru наследует IMAP-парсинг от Yandex. | Самостоятельно отправленное из обычной почты письмо в `Sent` не импортируется. Ключевой сценарий пока не работает. |
| Нормализация | Сохраняются provider ID, RFC `Message-ID`, `In-Reply-To`, `References`, From, один To, subject, text/HTML и время. | Основа для RFC-цепочки есть. Не сохраняются Cc, все получатели, папка, provider conversation ID и направление внешнего письма. |
| Привязка | Автоматически: `In-Reply-To`/`References`, затем `тема + email поставщика`; оба поиска ограничены одним ящиком. | Заголовки работают для известных ответов, но нельзя продолжить цепочку из другого ящика. Резервная эвристика слишком сильна. |
| Неразобранные письма | Есть «Письма без заявки», suggestions, ручная привязка и отмена ручной привязки. | Это правильный экран восстановления, но сейчас одно письмо физически копируется в историю при attach. |
| Аккаунты | Один provider на пару `user + workspace`; один cursor синхронизации на аккаунт. | Личный и корпоративный ящики одного provider и независимые cursors Inbox/Sent не поддерживаются. |

Проверено изолированными тестами: Yandex IMAP cursor и заголовки, сохранение
и дедупликация входящего ответа, а также Mail.ru IMAP/SMTP boundary. Реальные
провайдеры и ящики не открывались.

## Решение для MVP

### 1. Явная метка для первого письма

В заявке SupplyDesk показывает действие **«Скопировать тему для письма»**:

`[SD-1059] Запрос КП — кирпич М150`

Пользователь вставляет тему в обычный почтовый клиент. `SD-1059` —
неизменяемая публичная метка заявки; она не зависит от того, отправляет ли
SupplyDesk письмо сам. Для нового письма она является главным доказательством
принадлежности заявке.

Для будущей переносимости допускается заменить отображаемый номер на
непредсказуемый `SD-RQ-7K4P9M`, но в MVP `[SD-1059]` достаточно прост и
соответствует текущему глобальному первичному ключу заявки. Он не является
правом доступа: сервер всегда дополнительно проверяет workspace.

В тело можно добавлять строку `Request-ID: SD-1059` как дополнительную
подсказку, но не как скрытый механизм. Почтовые клиенты и поставщики могут
удалить или изменить текст тела; для первичного сопоставления тема надёжнее и
видна пользователю.

### 2. После первой привязки — нормальная почтовая цепочка

После найденной метки сохраняются и связываются RFC-заголовки. Дальше система
в первую очередь ищет пересечение `In-Reply-To` и `References` с уже известным
`Message-ID`, даже если поставщик поменял тему. Это работает для ответов с
личного или корпоративного ящика в одном разрешённом workspace.

Provider conversation/thread ID, если конкретный provider его отдаёт,
сохраняется как дополнительное доказательство, но не является обязательным
для общего алгоритма: у IMAP-провайдеров нет единого переносимого аналога.

### 3. Если доказательств нет — не угадывать

`Тема + адрес`, домен поставщика, похожие слова и ИИ создают только
предложение в «Письмах без заявки». Они никогда не создают автоматическую
связь. Пользователь выбирает заявку и, при необходимости, поставщика. Такая
связь обратима; будущие настоящие Reply можно распознать уже по сохранённым
заголовкам.

## Единый provider-neutral ingestion layer

Чтобы не делать отдельную логику и копии писем для каждого provider, вводится
один нормализованный входной контракт:

`mailbox_id, folder, provider_message_id, rfc_message_id, conversation_key?,`
`direction, from_addresses, to_addresses, cc_addresses, subject, body,`
`received_at, source_account_id`.

Yandex, Mail.ru и будущие адаптеры отвечают только за получение писем и
заполнение этого контракта. Matching и UI не знают о provider.

Каждое внешнее письмо хранится один раз как canonical source message. Его
связи с заявкой, поставщиком и цепочкой хранятся отдельно. Это устраняет
нынешнее копирование записи из «Без заявки» в `mail_messages` при ручной
привязке и позволяет одному письму нескольким адресатам иметь несколько
явных связей без дублирования текста/вложений.

## Алгоритм matching

Алгоритм останавливается на первом однозначном уровне. Несколько сильных,
но противоречивых результатов считаются конфликтом, а не выбором «первого».

| Приоритет | Доказательство | Результат |
| --- | --- | --- |
| A | Одна корректная `[SD-…]` метка, заявка существует в workspace | Автопривязать, причина `explicit_reference`. |
| B | `In-Reply-To`/`References` ведут ровно к одной ранее привязанной цепочке | Автопривязать, причина `rfc_thread`. |
| C | Однозначный provider conversation ID, уже связанный с заявкой | Автопривязать, причина `provider_thread`. |
| D | Точный адрес + нормализованная тема | Показать candidate, не привязывать. |
| E | Только домен, ключевые слова или AI | Показать candidate, не привязывать. |

Если письмо содержит явную метку, противоречащую RFC-цепочке, несколько меток
или неизвестную метку, оно получает состояние `conflict`/`invalid_reference`
и ждёт решения пользователя. Автоматическая привязка здесь запрещена.

## Необходимые изменения

### БД

1. У заявки появляется immutable `email_reference` с уникальным индексом;
   существующие заявки получают метку миграцией.
2. Один canonical источник внешнего письма получает `folder`, `direction`,
   список адресов, optional `provider_thread_key` и уникальные ключи
   provider/RFC-дедупликации.
3. `mail_sync_cursors` становятся отдельными на `mailbox + folder`, минимум
   `INBOX` и `Sent`.
4. Связь сообщения с заявкой/поставщиком получает `source`, `reason`,
   `confidence`, `active`, автора и audit trail. Отмена отключает связь, не
   удаляя письмо.
5. Несколько адресов одного provider поддерживаются по ID аккаунта, а не
   неявным выбором provider. Общий корпоративный mailbox имеет одну mailbox
   identity и несколько разрешённых пользователей, чтобы одно письмо не
   импортировалось каждым человеком повторно.

### Backend и sync

1. Добавить read-only folder sync для `Sent` наряду с `INBOX`; первый запуск
   показывает preview папок/даты и не загружает всю личную историю молча.
2. Нормализовать адреса From/To/Cc и определять направление по папке и
   подключённому адресу, не по догадке из текста.
3. Дедуплицировать сначала по стабильному provider key, затем по RFC
   `Message-ID` в рамках mailbox; совпадения с уже отправленным SupplyDesk
   письмом не создают вторую карточку сообщения.
4. Прогонять единый matcher, сохранять его решение и evidence. Retry должен
   быть идемпотентен: повторная синхронизация не создаёт новых писем или
   связей.

### Frontend

1. В карточке заявки: «Скопировать тему для письма» и «Скопировать ID».
2. В «Письмах без заявки»: причина, найденная метка/candidate и действия
   «Привязать», «Исправить связь», «Отменить привязку».
3. В истории заявки: откуда пришло письмо (личный/корпоративный ящик) и
   понятная, вторичная причина автосвязи; без внутреннего provider ID.
4. Личный ящик: непривязанные письма private-by-default. Перевод в
   workspace-контекст происходит только по явной привязке или выбранному
   правилу для strong matches.

## Конфликтные сценарии

| Ситуация | Поведение |
| --- | --- |
| Метку забыли | Письмо не привязывается автоматически; candidate/manual link. |
| Метка неверна или из другого workspace | `invalid_reference`, без автопривязки. |
| Две заявки одному поставщику | Адрес и тема лишь candidates; решает метка/RFC-цепочка/человек. |
| Поставщик начал новое письмо | Только метка даст автосвязь; иначе «Без заявки». |
| Поставщик изменил тему | Сохранённые RFC headers продолжают цепочку. |
| Пересылка сотруднику | Это новая связь, пока явная метка или человек не подтвердят её. |
| Несколько пользователей одного mailbox | Одна ingestion identity и дедупликация; права просмотра отделены от чтения ящика. |
| Один ответ подходит нескольким правилам | `conflict`; пользователь выбирает, система фиксирует evidence. |
| Закрытая заявка получила ответ | Письмо связывается и показывает предупреждение; заявку не переоткрывать автоматически. |
| Связь ошибочна | «Исправить/отменить» меняет relation и сохраняет audit; письмо остаётся. |

## Последовательность реализации

1. **SUP-029A — reference и UX:** `email_reference`, copy subject/ID,
   строгий parser, matcher A/B и tests. Без реального provider доступа.
2. **SUP-029B — inbox + sent ingestion:** folder cursors, единый
   нормализованный source message, dedupe и private visibility. Тесты на
   самостоятельное исходящее письмо, ответ и повторную синхронизацию.
3. **SUP-029C — mailbox sharing/conflicts:** несколько аккаунтов одного
   provider, shared mailbox identity, conflict-resolution UI и audit.
4. **SUP-029D — отдельная owner-acceptance:** подключение реального ящика,
   OAuth/app password и read-only preview. Никаких отправок или массового
   исторического импорта без отдельного согласия.

## Не входит в MVP

- обязательный переход пользователей в почтовый интерфейс SupplyDesk;
- автоматическая привязка по AI/похожей теме;
- скрытые ID в теле письма как единственный ключ;
- отдельные matching-алгоритмы для Yandex и Mail.ru;
- доступ к реальным ящикам, OAuth или массовый импорт без owner consent.
