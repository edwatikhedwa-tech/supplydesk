# Engineering Contract

Постоянные правила разработки SupplyDesk.

1. Автотесты и ручные проверки не должны изменять live/production data. Для
   тестов использовать изолированную базу и явно проверять её путь.
2. Любая destructive-операция выполняется только в порядке: backup → dry-run
   → validation → explicit apply. Без явного разрешения владельца apply не
   выполняется.
3. Frontend не является достаточной защитой критической бизнес-логики.
   Дубли, idempotency и race-sensitive операции защищаются backend/database.
4. Новая DB table/column/index добавляется нормальной migration; повторный
   запуск миграций должен быть безопасным.
5. Для race-sensitive flow обязательны проверки concurrency, rollback и
   idempotency. Happy-path test сам по себе не является acceptance.
6. Unrelated проблемы не исправляются в текущей задаче; они записываются в
   DEFERRED FINDINGS или текущий audit state.
7. Реальные email sends запрещены без отдельного явного разрешения. SMTP
   accepted означает принятие сервером отправителя, а не подтверждённую
   доставку во Inbox.
8. Supplier/company нельзя объединять только по названию. Identity должна
   иметь проверяемое основание (например, подтверждённый INN/global identity).
9. Каждый новый critical flow получает regression tests, включая отрицательные
   сценарии и защиту от повторного действия.
10. Если существенное бизнес-решение нельзя вывести из продукта, его нельзя
    угадывать: нужно запросить решение владельца.
11. После завершённого этапа обновляются CURRENT_STATE и WORK_LOG.
