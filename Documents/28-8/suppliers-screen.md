## 1. Ключевое архитектурное решение: два разных «поставщика»

В проекте теперь два уровня идентичности поставщика — это **осознанно**, не
дублирование:

- **`suppliers`** (существующая таблица) — identity по домену (`external_key`
  = host). Это то, что нужно краулеру и обогащению: два письма с одного
  домена — один и тот же `supplier_id`, поиск/обход работает пер-хост.
- **`global_suppliers`** (новая таблица) — identity по **ИНН**, в рамках
  рабочего пространства. Это то, что нужно снабженцу: одна компания — одна
  карточка, даже если её нашли под двумя разными доменами (два сайта одной
  фирмы, редизайн с переездом на новый домен и т.п.).

Связь — таблица `global_supplier_links` (`supplier_id` → `global_supplier_id`,
один host-supplier принадлежит максимум одной глобальной карточке). Карточка
создаётся/дополняется автоматически в `apply_supplier_enrichment()` в момент,
когда у host-supplier’а появляется ИНН, прошедший контрольную сумму — то есть
ровно та же точка, где уже работает обогащение из
[enrichment-and-cache.md](enrichment-and-cache.md). Отдельной формы ручного
создания карточки с нуля нет: GlobalSupplier остаётся производной от
проверяемого ИНН. При этом в карточке поставщика конкретной заявки пользователь
может внести корректный ИНН; он сохраняется с источником `manual`, запускает
обогащение Checko и тем же штатным путём создаёт либо дополняет GlobalSupplier.
Это не свободное ручное создание компании и не ослабляет модель доказательств.

`suppliers`, уже имевшие ИНН до этой миграции (fixture, прежние прогоны),
подхватываются через `MailRepository.backfill_global_suppliers()` — вызывается
при каждом старте процесса, идемпотентна (см. `supplier_app.py.SupplierApp.__init__`).

## 2. Модель данных

Три новые таблицы (`migrations/007_global_suppliers.sql`):

| Таблица | Назначение |
| --- | --- |
| `global_suppliers` | Карточка: ИНН, название, сайт, email, телефон, заметка, `is_favorite` |
| `global_supplier_links` | `supplier_id` → `global_supplier_id` |
| `global_supplier_issues` | Сообщения о проблемах: `reason`, `comment`, `correct_inn`, `source` (`manual`/`auto`), `reported_at` |
| `request_supplier_ratings` | Оценка сделки 1–5 по паре (заявка, host-supplier) |

**Почему не `ALTER TABLE`:** `ensure_schema()` выполняет каждый файл миграции
при **каждом** старте процесса (все существующие — через `CREATE TABLE/INDEX
IF NOT EXISTS`, идемпотентно). `ALTER TABLE ADD COLUMN` не идемпотентен и
уронил бы второй запуск. Поэтому связь и оценка — отдельные таблицы, не новые
столбцы в `suppliers`/`request_suppliers`.

**Что не хранится отдельно, а считается на лету** (в
`MailRepository.list_global_suppliers()` / `global_supplier_detail()`):
`total_requests`, `response_rate`, `avg_response_hours`, `last_contact_at`,
`avg_deal_rating`, `categories`, `relationship_status`. Все — агрегаты по уже
существующим таблицам (`request_suppliers`, `request_supplier_states`,
`mail_messages`, `request_positions`, `blacklist_entries`). Раз источник
истины уже есть, дублировать его в отдельных счётчиках означало бы рассинхрон
при любом ручном изменении данных — решили посчитать, а не кэшировать.

**Чёрный список — одна точка правды.** «Статус отношений: чёрный список» не
завёл вторую таблицу — использует существующий `blacklist_entries`
(`add_blacklist`/`restore_blacklist`, тот же механизм, что у страницы
`/blacklist`). Пометка в карточке глобального поставщика применяет
блокировку/восстановление ко **всем** привязанным host-suppliers сразу.

## 3. Найденный и исправленный по пути баг: словарь статусов

При проектировании агрегации обнаружилось, что `request_supplier_states.status`
хранит внутренние состояния конвейера отправки (`queued`, `sending`, `sent`,
`failed`, `replied`), а фронтенд (и API `list_suppliers`) ожидал
пользовательский словарь (`not_sent`, `sent`, `waiting`, `answered`, `error`).
Раньше `list_suppliers` отдавал сырое значение без преобразования — то есть
любой статус кроме дефолтного `not_sent` показывался бы в интерфейсе как
нераспознанное/пустое значение. Добавлена нормализация
(`_normalize_mail_status()` в `mail/repository.py`), применена и в
`list_suppliers`, и в новом коде истории заявок:

| Внутреннее состояние | Пользовательское |
| --- | --- |
| `queued`, `sending` | `sent` |
| `sent` (доставлено, ответа ещё нет) | `waiting` |
| `replied` | `answered` |
| `failed` | `error` |

## 4. Раздел 7 документа: автоматическое обнаружение проблем (bounce)

Реализовано в `mail/bounce.py` (`classify_bounce()`) + подключено в
`MailRepository.import_incoming_messages()` — том же коде, что уже читает
входящую почту и привязывает ответы к заявкам (буквально «тот же самый
механизм», как и просил документ).

- **«Жёсткий» bounce** (адрес не существует, домен не найден — паттерны вида
  `does not exist`, `550`, `нет такого адреса`) — надёжный сигнал:
  автоматически создаёт `global_supplier_issues` с `source='auto'`,
  `reason='email_invalid'`, и переводит `request_supplier_states.status` в
  `'failed'` вместо ошибочного `'replied'` (bounce — не ответ поставщика).
- **«Мягкий» bounce** (переполнен ящик, временная ошибка — `mailbox full`,
  `451`/`452`) — состояние заявки не трогается, проблема не создаётся:
  повод для повтора, не для пометки.
- Письмо, которое похоже на bounce-конверт, но без конкретного
  жёсткого/мягкого маркера, классифицируется как «мягкий» — соглашение в
  пользу меньшего числа ложных проблем, а не большего охвата.
- Одна и та же проблема не дублируется день в день (проверка на существующую
  auto-запись с тем же `reason` за сегодня перед вставкой).

**Ограничение, зафиксированное честно, как в документе:** обнаруживается
только bounce, который смог привязаться к треду (через `In-Reply-To`/
`References`/сопоставление по теме — та же логика, что и для обычных ответов).
Bounce, не привязавшийся к треду, оседает в `mail_inbox_messages` как
`unmatched` и **не** порождает авто-проблему — привязка «через
Final-Recipient в теле письма» не реализована (следующий шаг, если понадобится).

## 5. API

Новые эндпоинты (`supplier_app.py`):

- `GET /api/global-suppliers` — список карточек рабочего пространства.
- `GET /api/global-suppliers/<id>` — карточка + история по заявкам + проблемы + `registry` (см. §5.1).
- `POST /api/global-suppliers/<id>` — `{note}`.
- `POST /api/global-suppliers/<id>/relationship` — `{status: none|favorite|blacklisted}`.
- `POST /api/global-suppliers/<id>/issues` — `{reason, comment?, correct_inn?, blacklist?}`.
- `POST /api/requests/<id>/suppliers/<id>/rating` — `{rating: 1..5}`.

### 5.1. Мини-инфографика реестра и финансов (25 августа 2026)

`global_supplier_registry` (`migrations/008_supplier_registry.sql`) хранит `ogrn`, `status`, `is_active`, `registered_at`; `global_supplier_finances` (`migrations/009_supplier_finances.sql`) хранит `report_year`, `revenue`, `profit` — по одной строке на `global_supplier`, обе 1:1. Заполняются в `apply_supplier_enrichment()` (`mail/repository.py`) тем же вызовом, что уже сверяет email/ИНН.

**Источник выручки/прибыли подтверждён по официальной документации** (https://checko.ru/integration/api, `/finances`), не придуман: отдельный метод `GET https://api.checko.ru/v2/finances?key=...&inn=...`, входит в тот же бесплатный тариф «Лайт» (100 запросов/сутки на все методы, без отдельной тарификации для этого метода). `checko_client.CheckoClient.finances()` вызывает его и берёт последний доступный отчётный год из `data`; коды строк `2110`/`2400` — это не поле, придуманное Checko, а стандартные коды формы №2 «Отчёт о финансовых результатах» (приказ Минфина №66н, ОКУД 0710002): 2110 = выручка, 2400 = чистая прибыль (отрицательное значение — убыток).

**Ротация ключей Checko** (`checko_client._load_keys`/`CheckoClient._get`): при HTTP 403 с признаком исчерпанного дневного лимита клиент сам переключается на следующий ключ из `CHECKO_KEY`, `CHECKO_KEY_2`, `CHECKO_KEY_3`... (см. `.env`). Один и тот же лимит (100/сутки) действует на все методы API суммарно, не по отдельности на `/company` и `/finances`.

Отображение — `SupplierPanel.tsx`, тонкая горизонтальная строка между шапкой карточки и блоком «Контакты»: возраст, статус, выручка, прибыль (цвет/стрелка меняются на «вниз»/красный при убытке), ссылка на профиль Checko — иконка + значение + короткая подпись, hover-тултип с расшифровкой и годом отчёта, скрывается целиком при отсутствии данных. При всех пяти показателях сразу строка шире панели (440px) и **скроллится по горизонтали** (`overflow-x-auto`) — это сознательный компромисс между «не увеличивать высоту» и уместить всё; проверено вживую, работает.

**Живая проверка обоих состояний прошла** на карточке ООО «Строительные системы» (ИНН 2312200792, `stroisyst.ru`):
- «данных нет» — строка не рендерится, высота карточки не меняется;
- «данные есть» — реальный ответ Checko (после переключения на второй ключ, первый исчерпал 100/сутки): 13 лет на рынке, «Действует», выручка 490 млн ₽ и прибыль 6,6 млн ₽ за 2025 год, ссылка на профиль — всё отображается корректно, скролл строки работает.

**Ссылка на профиль Checko — подтверждена живыми запросами 26.08.2026:**
`checko.ru/company/{ОГРН}` → 200, `checko.ru/entrepreneur/{ОГРНИП}` → 200,
`checko.ru/company/{ОГРНИП}` → **404**. То есть у организаций и ИП разные
пути, и выбирать надо по номеру: ОГРНИП — 15 цифр, ОГРН — 13. Это правило
живёт в `checkoProfileUrl()` (`RegistryFinanceRow.tsx`) и не требует
дополнительного поля из API. Попутно исправлено чтение самого номера:
`checko_client._fill()` брал только `ОГРН`, из-за чего у всех ИП номер
оставался пустым и ссылка не строилась вовсе.

### 5.2. Отображение в таблицах: своя колонка на каждый факт (26 августа 2026)

Первая версия показывала факты Checko одной слитной строкой под ИНН
(`RegistryMiniBadge`). По требованию владельца проекта это разнесено: у
каждого показателя своя колонка — **Возраст · Выручка · ЕГРЮЛ · Checko** —
и в таблице заявки (`components/SupplierTable.tsx`), и в картотеке
поставщиков, и в чёрном списке (`GlobalSupplierTable.tsx`).

Ячейки вынесены в общий модуль (`AgeCell`, `RevenueCell`, `ProfitCell`,
`RegistryStatusCell`, `CheckoLinkCell` в
`components/suppliers/RegistryFinanceRow.tsx`), поэтому правка формата или
подсказки чинит все три экрана сразу, а не один из них.

**Пустое значение — прочерк, не ноль.** В таблице прочерк удерживает
выравнивание колонки и честно говорит «значения нет», в отличие от нуля,
который читался бы как «выручка равна нулю».

**Ширины колонок заданы явно** (`gridTemplateColumns`, одна константа на
шапку и строки — разъехаться они не могут). Фиксированная ширина у коротких
предсказуемых фактов, `minmax()` — только у названия, контактов и
специализации. Именно «резиновые» колонки в прежней версии оставляли
пустоту в пол-экрана между контактами и статусом при коротком названии.

## 6.1. Экран «Чёрный список» (25 августа 2026)

Раньше `/blacklist` был отдельным, написанным с нуля экраном поверх старой host-based таблицы `blacklist_entries` — не переиспользовал вёрстку `/suppliers` и не знал про `global_suppliers`. Переделано по прямому требованию владельца проекта: единая таблица `GlobalSupplierTable` (`frontend/src/components/suppliers/GlobalSupplierTable.tsx`) с проп `view: 'all' | 'blacklist'`, используется и на `/suppliers`, и на `/blacklist` — разные колонки и пустое состояние, одна и та же механика выбора/клика/открытия карточки.

**Уточнение по терминологии из ТЗ:** формулировка задания предполагала, что на `/suppliers` уже есть отдельный переиспользуемый компонент `SupplierTable`. По факту его не было — таблица была инлайн-разметкой внутри `Suppliers.tsx`, а `components/SupplierTable.tsx` (уже существовавшее имя) — это другой, не связанный компонент для списка поставщиков внутри конкретной заявки (`/requests/:id`), с другой формой данных (`Supplier`, не `GlobalSupplier`). Поэтому общий компонент назван `GlobalSupplierTable`, чтобы не путать с уже существующим — само требование «не дублировать код таблицы» выполнено, только под более точным именем.

Причина блокировки (`blacklistReason`) и дата (`blacklistedAt`) — новая таблица `global_supplier_blacklist` (`migrations/010_supplier_blacklist_reason.sql`, 1:1 с `global_suppliers`, тот же принцип «новая таблица, не ALTER», что и во всех предыдущих миграциях этого экрана). Причина обязательна на уровне backend (`MailRepository.set_global_supplier_relationship` бросает `ValueError`, API отвечает 400), а не только на фронтенде — проверено вживую прямыми запросами к API: попытка без причины отклонена, с причиной — принята и видна в списке, восстановление (`status: 'none'`) корректно очищает причину и дату.

Два источника причины, оба ведут в один и тот же механизм:
- ручное переключение сегмента «Чёрный список» на карточке — теперь открывает встроенную мини-форму с обязательным полем причины вместо мгновенного переключения;
- чекбокс «Также пометить как чёрный список» в «Сообщить о проблеме» — использует код выбранной причины (`wrong_details`/`email_invalid`/...) как причину блокировки, тот же словарь `issueReasonLabels`, что и у списка проблем.

Побочно исправлено: `pluralize()` (`frontend/src/lib/utils.ts`) — общий helper для склонения числительных, которого не было (заявленное в ТЗ «как уже поправили на /suppliers» на самом деле не было сделано: там было жёстко "N поставщиков в базе"). Применён на `/suppliers` и `/blacklist` одинаково.

## 7. Статус

Реализовано на 25 августа 2026:

- модель данных, дедупликация по ИНН, автоматическая привязка при обогащении;
- список с фильтрами (Все/Избранные/Чёрный список/Давно не было
  контакта/Никогда не отвечали), поиском, массовым выбором и «создать заявку
  с выбранными»;
- карточка: статус отношений (сегмент из 3 кнопок), контакты, специализация,
  статистика (всего заявок, % ответов, средняя оценка сделки, среднее время
  ответа), заметка, история по заявкам с оценкой сделки по клику, «Сообщить о
  проблеме» с разметкой manual/auto;
- автоматическое обнаружение жёсткого bounce, подключённое к реальной
  IMAP-синхронизации;
- попутный фикс словаря статусов (`_normalize_mail_status`), затрагивающий и
  существующий экран заявки, не только новый экран.

Проверено вживую: 69 карточек агрегированы из данных, накопленных за все
тестовые прогоны сессии; смена статуса на «Избранный» сохраняется и сразу
отражается в фильтре; правки прошли полный набор из 31 backend-теста.

Не реализовано (осознанно отложено — соответствует приоритету 5–6 из
исходного документа, «можно отложить без большого риска»):

- **Импорт своей базы (CSV/Excel)** — UI-заглушка в референсе не подключена;
  нужен реальный парсер + сопоставление колонок + предпросмотр.
- **Экспорт в CSV** — не реализован.
- **Слияние дублей (Merge)** — не нужно в частом случае (дедупликация по ИНН
  уже автоматическая), но для случая «опечатка в ИНН → два разных ИНН на одну
  компанию» ручного слияния карточек пока нет.
- **Ручное добавление поставщика с нуля** — сознательно не переносилось из
  референса: GlobaSupplier — производная от обогащения (проверенный ИНН), а
  не самостоятельно вводимая пользователем сущность.

Не проверено:

- Обнаружение bounce на реальном, а не тестовом почтовом трафике (нет живых
  bounce-писем за время разработки — логика проверена только на синтетических
  сабджектах/примерах в `mail/bounce.py`, юнит-тестов на неё пока нет).
- Поведение при очень большом числе карточек (сотни+) — агрегация сейчас
  строится на Python-стороне из нескольких SQL-запросов, не рассчитана на
  постраничную загрузку.

**Известный остаточный артефакт:** карточка «Атлантис» (пример ложного
сопоставления ИНН из первого прогона обогащения, до фикса
`registry_owns_site`) уже была создана в базе с некорректным названием
компании до того, как исправление было внесено — новый фикс не откатывает
задним числом уже сохранённые данные, только предотвращает новые ложные
