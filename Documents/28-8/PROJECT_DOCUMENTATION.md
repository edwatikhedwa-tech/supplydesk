## 1. Назначение проекта

Supplydesk помогает снабженцу:

1. создать заявку с одной или несколькими позициями;
2. найти поставщиков по каждой позиции через XMLRiver и Яндекс;
3. проверить найденные компании и их контакты;
4. выбрать поставщиков для контакта;
5. подключить рабочую Яндекс.Почту через OAuth;
6. подготовить и отправить персонализированные запросы;
7. хранить исходящие и входящие сообщения в отдельных тредах по связке «заявка + поставщик».

Главный пользовательский сценарий:

```text
Заявка → отдельные позиции → поиск поставщиков → проверка → подготовка писем → очередь → переписка
```

Важно: кнопка отправки письма запускает реальную отправку. Для проверки интерфейса можно создать заявку и запустить поиск, но не нажимать «Отправить выбранным».

## 2. Текущее состояние

В проекте уже есть:

- вход через аккаунт Яндекса; локальный вход по паролю оставлен резервным для разработки;
- выход из кабинета и раздача страницы без данных для неавторизованного посетителя;
- **frontend — React SPA** (`frontend/`, см. раздел 3): рабочий стол, заявки, поставщики (CRM-картотека по ИНН), переписка и чёрный список;
- позиции заявки задаются одним полем — наименованием: позиция это поисковый запрос, количество в поиске не участвует;
- фоновый поиск поставщиков по позициям, глубина настраивается `SERP_PAGES`, обрабатываются **все** найденные сайты без искусственного потолка (`SERP_RESULTS_PER_POSITION` по умолчанию пуст — правило «сколько нашли, столько и обрабатываем»);
- **реальное извлечение контактов подключено к поиску** (не только CLI): краулинг сайта → регулярка на email/ИНН → LLM-фоллбэк на неоднозначных случаях → веб-поиск-фоллбэк (XMLRiver+Яндекс) для сайтов, недостижимых для краулера (антибот/бан/DNS-сбой) → сверка с реестром Checko. Подробности, актуальные цифры и защита от ложной привязки ИНН — в [enrichment-and-cache.md](enrichment-and-cache.md);
- сохранение поставщиков и связей «поставщик — позиция», плюс отдельная CRM-картотека `global_suppliers` по ИНН (одна карточка на компанию, даже если её нашли на двух доменах) — см. [suppliers-screen.md](suppliers-screen.md);
- Yandex OAuth, refresh token и SMTP XOAUTH2;
- шифрование OAuth-токенов на сервере;
- отправка одному или нескольким поставщикам отдельными письмами;
- очередь писем с ограничением параллелизма, retry и exponential backoff;
- IMAP XOAUTH2-синхронизация входящих сообщений;
- сопоставление входящих сообщений с тредами, включая автоматическое распознавание жёсткого bounce (см. [suppliers-screen.md](suppliers-screen.md) раздел 4);
- отдельный список неразобранных входящих;
- показ писем в исходной вёрстке: санитизация по белому списку плюс изолированный iframe, внешние картинки заблокированы;
- локальное SQLite-хранилище и PostgreSQL/Neon для production;
- адаптер Vercel Functions.

### Демонстрационная заявка и реальные заявки

Старый `supplier_finder.html` (с константой `DATA`) архивирован в `_archive/frontend-legacy/` после перехода на React SPA. Backend при инициализации по-прежнему синхронизирует демонстрационный каталог для заявки №1043 (теперь через фикстуру в коде, не через HTML-файл), поэтому заявка «Строительные материалы» доступна сразу после первого локального входа.

Для заявки №1043 endpoint запуска поиска намеренно возвращает уже готовый fixture и не делает новый внешний запрос. Для всех новых заявок поиск действительно обращается к XMLRiver, если в окружении заполнены `XMLRIVER_USER` и `XMLRIVER_KEY`, и полный конвейер обогащения (см. выше) реально извлекает контакты — это больше не CLI-only функциональность.

Это разделение по-прежнему важно при тестировании:

- №1043 — стабильные демонстрационные данные/fixture;
- новая заявка — реальный pipeline поиска, обогащения и сохранения результатов;
- наличие поставщика в fixture не означает, что он будет найден текущим внешним поиском в тех же деталях.

## 3. Архитектура

### Frontend

Frontend — React SPA в `frontend/` (Vite + TypeScript + Tailwind), собирается в `frontend/dist/` и раздаётся тем же Python backend'ом (заменил старый монолитный `supplier_finder.html`, который архивирован в `_archive/frontend-legacy/`, не удалён). Никаких сторонних BaaS (Supabase и т.п.) — весь фронтенд ходит только в `/api/*` этого backend'а.

Клиентский роутинг — `react-router` (`BrowserRouter`), backend отдаёт `frontend/dist/index.html` на любой несовпавший с `/api/*`/`/oauth/*` GET-путь (SPA fallback).

Основные разделы интерфейса:

- `Рабочий стол` — сводка и быстрые действия;
- `Мои заявки` — список и статусы заявок;
- `Поставщики` — CRM-картотека по ИНН: список с фильтрами/поиском/массовым выбором и карточка компании (статус отношений, контакты, статистика, история заявок, «сообщить о проблеме») — подробности в [suppliers-screen.md](suppliers-screen.md);
- `Переписка` — треды, входящие и исходящие сообщения;
- `Чёрный список` — исключённые компании;
- `Настройки · Почта` — подключение и проверка Яндекс.Почты.

### Backend

Backend — Python без web-фреймворка:

- [`supplier_app.py`](../../supplier_app.py) — локальный HTTP-сервер, маршрутизация API, сессии, OAuth callback и запуск фоновых задач;
- [`api/index.py`](../../api/index.py) — адаптер для Vercel Functions;
- `http.server.ThreadingHTTPServer` — локальный сервер;
- `ThreadingHTTPServer` и отдельные daemon-потоки — фоновые операции поиска;
- `MailQueue` — очередь отправки писем.

ORM не используется. Доступ к данным реализован через небольшой DB-API-репозиторий [`mail/repository.py`](../../mail/repository.py), который поддерживает SQLite и PostgreSQL.

### Что происходит при старте

Локальный запуск проходит в таком порядке:

```text
supplier_app.py
  → load_dotenv(.env)
  → Config.from_env()
  → MailRepository.ensure_schema()
  → seed_user() и создание workspace
  → seed_fixture_catalog() для демонстрационной заявки №1043
  → MailService + MailQueue
  → HTTP-сервер на APP_HOST:PORT
```

Особенности инициализации:

1. значения, уже заданные в окружении процесса, имеют приоритет над `.env`;
2. миграции `migrations/*.sql` применяются при каждом старте идемпотентно;
3. после Iteration 1 recovery различает legacy/неподтверждённые `sending`: до
   irreversible gate запись возвращается в `queued`, после gate становится
   `delivery_unknown`;
4. локальная очередь стартует вместе с сервером;
5. если `DATABASE_URL` задан, используется PostgreSQL, иначе создаётся SQLite-файл по `MAIL_DB_PATH`.

Исторически на Vercel `api/index.py` создавал экземпляр `SupplierApp` и мог
запускать очередь для тёплого serverless-инстанса. Этот serverless-адаптер не
является поддерживаемым рабочим контуром почтовой очереди: для неё нужен
постоянный локальный/обычный процесс и durable база. Сам адаптер в Iteration 1
не удалялся.

### Почтовая абстракция

Провайдер почты отделён от бизнес-логики:

```text
mail/providers/base.py       общий контракт провайдера
mail/providers/yandex.py     OAuth, SMTP и IMAP для Яндекс.Почты
mail/service.py               шаблоны, персонализация и бизнес-правила
mail/queue.py                 очередь и retry
mail/repository.py            сохранение аккаунтов, тредов и сообщений
```

Новый Gmail или Outlook-провайдер должен реализовать тот же контракт, не меняя модели тредов и сообщений.

## 5. Локальный запуск

### Требования

- Windows, macOS или Linux;
- Python 3.11+;
- доступ к XMLRiver для реального поиска;
- SQLite используется по умолчанию; PostgreSQL подключается при заданном
  `DATABASE_URL` в любом постоянном контуре.

### Установка

PowerShell:

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
Copy-Item .env.example .env
```

Заполните `.env`. Реальный файл `.env` нельзя коммитить или пересылать.

### Минимальный запуск интерфейса

```powershell
python supplier_app.py
```

Откройте:

```text
http://127.0.0.1:8000/
```

Если порт занят:

```powershell
$env:PORT = "8765"
python supplier_app.py
```

Тогда адрес будет `http://127.0.0.1:8765/`.

### Вход

Основной способ — кнопка «Войти с помощью Яндекса» на экране входа. Для локального запуска нужно **отдельное** приложение Яндекс OAuth с Redirect URI `http://127.0.0.1:8000/oauth/yandex/callback`: у приложения одно поле Redirect URI, поэтому боевое приложение переиспользовать нельзя, не сломав вход на сайте. Его `YANDEX_CLIENT_ID` и `YANDEX_CLIENT_SECRET` прописываются в локальный `.env`.

Пользователь и рабочее пространство создаются автоматически при первом входе.

Резервный вход по паролю доступен на уровне backend API для локальной
диагностики, но на текущем экране входа не показывается. Он использует:

```text
APP_USER_EMAIL=
APP_USER_PASSWORD=
```

Ролей, приглашений и разделения прав внутри рабочего пространства пока нет.

## 6. Переменные окружения

Все значения ниже должны храниться только в `.env` локально или в Vercel Environment Variables.

| Переменная | Обязательность | Назначение |
|---|---:|---|
| `XMLRIVER_USER` | для реального поиска | ID пользователя XMLRiver |
| `XMLRIVER_KEY` | для реального поиска | ключ XMLRiver |
| `APP_HOST` | нет | адрес локального сервера, обычно `127.0.0.1` |
| `PORT` | нет | порт, по умолчанию `8000` |
| `APP_BASE_URL` | да для OAuth | базовый URL приложения |
| `APP_USER_EMAIL` | для резервного локального входа | email пользователя разработки |
| `APP_USER_PASSWORD` | для резервного локального входа | пароль пользователя разработки |
| `MAIL_DB_PATH` | локально | путь к SQLite-файлу |
| `DATABASE_URL` | production | PostgreSQL/Neon connection string |
| `MAIL_TOKEN_ENCRYPTION_KEY` | для OAuth | ключ AES-256-GCM шифрования токенов |
| `MAIL_QUEUE_CONCURRENCY` | нет | параллелизм очереди, backend ограничивает максимум до 4 |
| `MAIL_MAX_RETRIES` | нет | максимум повторов, backend ограничивает максимум до 8 |
| `MAIL_DAILY_RECIPIENT_LIMIT` | нет | дневной лимит получателей |
| `YANDEX_CLIENT_ID` | да | Client ID приложения Яндекс OAuth — нужен и для входа, и для почты |
| `YANDEX_CLIENT_SECRET` | да | Client Secret приложения Яндекс OAuth |
| `YANDEX_REDIRECT_URI` | да | callback URI, должен совпадать с настройкой приложения буквально |
| `YANDEX_OAUTH_SCOPE` | нет | по умолчанию `mail:smtp mail:imap_full login:email` |
| `DADATA_TOKEN` | для проверки ИНН | токен DaData |
| `ANTHROPIC_API_KEY` | только для `--llm` | необязательный LLM fallback |
| `ROUTERAI_KEY` | для LLM-ступени | ключ RouterAI, см. [enrichment-and-cache.md](enrichment-and-cache.md) |
| `CHECKO_KEY` | для данных ЕГРЮЛ | ключ Checko: название, статус, ОКВЭД, контакты, риски |

У локального запуска и production разные приложения Яндекс OAuth, потому что поле Redirect URI одно на приложение: локальное смотрит на `http://127.0.0.1:8000/oauth/yandex/callback`, боевое — на адрес Vercel. Менять Redirect URI боевого приложения ради локальной отладки нельзя: это ломает вход на сайте.

Сгенерировать ключ шифрования можно так:

```powershell
python -c "from mail.crypto import generate_key; print(generate_key())"
```

В репозитории не должны находиться реальные пароли, API-ключи, OAuth-токены или содержимое `.env`.

## 7. Жизненный цикл заявки

### Создание

В форме «Новая заявка» каждая позиция добавляется отдельной строкой. У строки есть собственные плейсхолдеры:

- `Например, Кирпич М150`;
- `Например, 12 000 шт`.

Frontend отправляет backend массив объектов:

```json
{
  "name": "Труба ПВХ 110 мм",
  "quantity": "100 м"
}
```

Backend сохраняет строки в `request_positions` с ключами `p1`, `p2` и т. д. Старый формат свободного текста с разделителем `|` временно поддерживается для обратной совместимости API.

Одновременно создаются:

- строка в `requests` — название, описание, отправитель и компания;
- строка в `request_meta` — `draft`, прогресс поиска и возможная ошибка;
- строки в `request_positions` — нормализованные позиции;
- запись `audit_events` — действие `request.created`.

До запуска поиска поставщики не создаются и письма не ставятся в очередь.

### Поиск

1. Пользователь нажимает «Начать поиск».
2. Backend меняет статус заявки на `searching`.
3. Фоновый worker обрабатывает позиции по очереди.
4. Для каждой позиции выполняется запрос XMLRiver с суффиксом `купить`.
5. Результаты дедуплицируются по host.
6. До 30 результатов каждой позиции сохраняются в БД.
7. Поставщики связываются с позициями в `request_suppliers`.
8. После завершения статус меняется на `completed`.

Каждый новый результат обновляет/создаёт запись в `suppliers`, профиль в `supplier_profiles` и связь в `request_suppliers`. Если один и тот же host найден по двум позициям, компания хранится один раз, а список покрываемых позиций хранится в связи заявки.

Статусы заявки:

```text
draft → searching → completed
                  ↘ error
```

`POST /api/requests/{id}/search` обычно отвечает `202` сразу после постановки задачи. UI затем повторно загружает список заявок и видит итоговый статус. В одном процессе одновременно разрешён только один search worker; повторный запуск другой заявки до его завершения вернёт понятную ошибку.

В текущем интерфейсе после `completed` показывается: «Готово к отправке запросов». Это означает, что поставщики найдены, но письма ещё не отправлялись.

### Отправка

Отправка не выполняется автоматически после поиска. Пользователь сам выбирает поставщиков и нажимает «Написать» или «Отправить выбранным».

Для каждого поставщика создаются:

- отдельное письмо;
- отдельная job в `mail_jobs`;
- отдельный тред в `mail_threads`;
- отдельный статус в `request_supplier_states`.

CC/BCC для массовой отправки не используется.

Статусы поставщика:

```text
not_sent → queued → sending → sent
                         ↘ failed
```

Временная ошибка провайдера переводит job обратно в `queued` с ограниченным retry и увеличенной задержкой. Постоянная ошибка становится `failed` и отображается пользователю.

Очередь ограничена параметрами `MAIL_QUEUE_CONCURRENCY` и `MAIL_MAX_RETRIES` (пределы backend: от 1 до 4 workers и не более 8 повторов). Обычный retry использует exponential backoff с небольшим jitter и максимумом 15 минут. Ошибка rate limit ставит очередь на паузу примерно на час. После перезапуска процесса незавершённые `sending` jobs возвращаются в `queued`.

## 9. Авторизация и доступ к данным

### Вход через Яндекс — основной способ

1. `/api/auth/yandex/start` начинает поток, когда сессии ещё нет: генерирует `state` и PKCE-пару, сохраняет их в `oauth_login_states` и кладёт `state` в отдельную cookie с областью действия `/oauth/yandex/callback`;
2. `/oauth/yandex/callback` — общий callback. Он сначала пробует трактовать `state` как подключение почты (требует существующую сессию), затем как вход; вход принимается только если `state` из БД совпадает с тем, что в cookie;
3. по коду выдаётся токен, из профиля берётся email, `get_or_create_oauth_user()` находит или создаёт пользователя и его рабочее пространство;
4. тот же грант сразу сохраняется как почтовый аккаунт — отдельно подключать ящик не нужно. Если шифрование токенов не настроено, вход всё равно завершается успешно, а почта остаётся неподключённой.

Пользователь, созданный через OAuth, не имеет пригодного пароля: в `password_hash` пишется хеш случайного токена, поэтому войти по паролю под таким аккаунтом нельзя.

Локальный вход по `APP_USER_EMAIL`/`APP_USER_PASSWORD` остаётся резервным
backend-сценарием для разработки. На текущем экране входа кнопки «Локальный
вход для разработки» нет; основной видимый путь — Яндекс OAuth.

### Общая механика сессии

1. backend создаёт случайный session token и CSRF token;
2. session token уходит в `HttpOnly` cookie `session_id` с `SameSite=Lax` (и `Secure` на HTTPS);
3. в БД сохраняются только хеши session и CSRF token;
4. session действует 8 часов;
5. каждый защищённый запрос получает `user_id` и `workspace_id` из сессии;
6. SQL-запросы дополнительно фильтруют данные по workspace.

Все изменяющие POST-запросы требуют заголовок `X-CSRF-Token`. Для POST API действует ограничение 30 запросов за 60 секунд на session token.

OAuth state живёт 10 минут и используется однократно. PKCE использует `S256`. State подключения почты дополнительно привязан к конкретной session/user/workspace; state входа привязан к cookie, так как сессии в этот момент ещё нет.

### Данные до входа

Страница приложения отдаётся сервером динамически. Без действующей сессии в неё подставляется пустой набор данных, поэтому анонимный посетитель не получает ни контактов поставщиков, ни адреса пользователя. Реальные данные попадают в ответ только вместе с валидной cookie.

Это по-прежнему не полноценная multi-tenant система: workspace создаётся автоматически на каждого нового пользователя Яндекса, ролей и приглашений нет.

## 10. Почта и OAuth

Подробная инструкция находится в [`mail-integration.md`](mail-integration.md). Краткая схема:

```text
Подключить Яндекс Почту
        ↓
OAuth authorization code + state + PKCE
        ↓
callback /oauth/yandex/callback
        ↓
обмен code на access/refresh token
        ↓
получение email аккаунта
        ↓
AES-256-GCM шифрование токенов
        ↓
SMTP XOAUTH2 / IMAP XOAUTH2
```

Используемые scopes:

- `mail:smtp` — отправка;
- `mail:imap_full` — чтение входящих по IMAP;
- `login:email` — email подключённого аккаунта.

Токены никогда не должны попадать во frontend, API-ответы или логи. Пароль от почты приложение не запрашивает.

### Что происходит при отправке письма

1. Frontend передаёт `request_id`, одного поставщика или массив поставщиков, тему, текст и вложения.
2. `MailService` проверяет текущую сессию, workspace, подключённый mail account, email получателя, тему, текст и вложения.
3. При необходимости просроченный access token обновляется через refresh token; новые токены снова шифруются и сохраняются.
4. Текст шаблона персонализируется переменными `{{supplier_name}}`, `{{request_name}}`, `{{request_description}}`, `{{sender_name}}`, `{{company_name}}`.
5. Репозиторий собирает operation в состоянии `assembling`; после появления
   всех ожидаемых targets операция становится `ready`, затем создаются
   `mail_message`/`mail_job` и supplier state переводится в `queued`.
6. Worker забирает только ready-job, фиксирует claim/lease и durable
   irreversible gate, затем вызывает `YandexMailProvider.send_message()`.
7. После provider success локальный result фиксируется первым, а затем
   best-effort сохраняется отдельная копия в `\\Sent`.
8. Явный отказ до acceptance использует bounded retry/`failed`; timeout,
   disconnect или ошибка локальной записи после gate переводят запись в
   `delivery_unknown` и не запускают обычный retry.

Таким образом, запись `sent` в интерфейсе появляется только после
положительного ответа провайдера; это не доказательство доставки в ящик и не
подтверждение прочтения. Неопределённый результат показывается отдельно как
`delivery_unknown`.

Для production callback должен быть зарегистрирован в Яндекс OAuth буквально, например:

```text
https://your-domain.example/oauth/yandex/callback
```

## 11. Входящие сообщения

Синхронизация выполняется через IMAP XOAUTH2 и UID-курсор:

1. читается папка `INBOX`;
2. используется `BODY.PEEK[]`, чтобы не менять статус прочитанности;
3. сначала проверяются `In-Reply-To` и `References`;
4. затем используется безопасное сопоставление по теме и адресу поставщика;
5. найденное письмо добавляется в `mail_messages` как `direction=inbound`;
6. письмо без безопасной связи сохраняется в `mail_inbox_messages`;
7. повторный sync не создаёт дубликат.

### Как показывается письмо

При приёме сохраняется собственный HTML отправителя, а `text/plain` остаётся запасным вариантом. Раньше парсер выбрасывал HTML-часть и собирал «HTML» из текста, заменяя переводы строк на `<br>`, — ссылки, списки и таблицы уничтожались на входе, и никакой рендер их уже не восстанавливал.

Показ письма защищён двумя независимыми слоями:

1. `sanitize_email_html()` оставляет только разрешённые теги и атрибуты, вырезает `script`, `iframe`, `form`, `svg`, обработчики событий и атрибут `style`, а из ссылок — небезопасные схемы; внешние ссылки получают `rel="noopener noreferrer nofollow"`;
2. результат рендерится в `<iframe sandbox>` без единого разрешения и с запрещающим CSP, поэтому скрипт не выполнится, даже если проскочит мимо санитайзера.

Внешние изображения по умолчанию не загружаются, и об этом есть видимая пометка: картинка в письме — обычный способ отследить факт прочтения. Встроенные `data:`-изображения показываются.

Письма, сохранённые до этого изменения, остались с прежним испорченным HTML — исправление действует на вновь синхронизированные.

Основные таблицы:

- `users`, `workspaces`, `workspace_members`, `sessions`, `oauth_states`;
- `requests`, `request_meta`, `request_positions`;
- `suppliers`, `supplier_profiles`, `request_suppliers`, `request_supplier_states`;

Связь переписки:

```text
workspace + request + supplier → mail_thread
mail_thread → mail_messages
mail_message → mail_job (для исходящего письма)

```

Миграции применяются репозиторием при инициализации. Для production используется PostgreSQL через `DATABASE_URL`; для локального режима — SQLite по пути `MAIL_DB_PATH`.

На Vercel нельзя полагаться на SQLite в `/tmp` для постоянных данных: serverless-инстанс эфемерен. Production должен использовать Neon/PostgreSQL.

## 15. Безопасность и операционные правила

- не хранить секреты в Git;
- не передавать OAuth-токены во frontend;
- не выводить access/refresh token в логи;
- не использовать пароль пользователя для доступа к почте;
- проверять session, workspace и CSRF на каждом изменяющем endpoint;
- раздавать статику только по белому списку: любой файл проекта, попавший в раздачу, становится публичным (так уже случалось — наружу отдавались исходники и миграции);
- не встраивать реальные данные в статическую страницу: страница приложения собирается на сервере и получает данные только при валидной сессии;
- не выводить HTML письма без санитайзера и изолирующего iframe одновременно;
- не отправлять массовую рассылку через CC/BCC;
- соблюдать лимиты XMLRiver и Яндекс.Почты;
- ограничивать retry и concurrency;
- при rate limit останавливать или замедлять очередь;
- валидировать email, размер и тип вложений;
- экранировать текст писем;
- не считать SMTP-индикацию успешной, пока провайдер не подтвердил отправку;
- перед изменением схемы добавлять отдельную миграцию, а не переписывать существующую.

## 16. Ограничения текущей версии

- **обогащение внутри одной заявки идёт последовательно**: краулинг распараллелен (5 воркеров), но веб-поиск-фоллбэк и LLM-ступень для каждого сайта — один за другим в простом цикле (`_enrich_suppliers` в `supplier_app.py`). На глубине `SERP_PAGES=10` (≈70-80 сайтов) это ощутимо — заявка может обрабатываться несколько минут, это ожидаемая цена правила «обрабатываем всё, что нашли», не зависание;
- **нет общего кэша**: выдача и результаты обхода сайтов привязаны к рабочему пространству (`UNIQUE (workspace_id, external_key)`), поэтому разные пользователи по одному ключу тратят платные запросы повторно;
- **реестр Checko используется для обогащения после автоматического или ручного ИНН**: пользователь может ввести корректный ИНН в карточке поставщика конкретной заявки; отдельной формы создания глобальной карточки «с нуля» нет;
- вход через Яндекс работает; локальный вход по паролю остаётся резервным для разработки;
- поиск запускается как возобновляемая очередь шагов: курсор и lease хранятся в `request_search_jobs`, поэтому перезапуск Vercel не теряет заявку;
- входящие синхронизируются вручную/при открытии раздела, постоянного webhook/push нет;
- полноценная история папок Sent/Drafts ещё не реализована как отдельный mail client;
- Gmail и Outlook пока не подключены;
- очередь отправки почты по-прежнему находится внутри процесса и не заменяет отдельный production worker;
- поиск на Vercel теперь надёжен при открытой странице заявки: браузер последовательно вызывает короткий `/search/step`, а прерванный шаг можно забрать после истечения lease; для полностью автономного поиска при закрытом браузере позже понадобится внешний worker или Neon Function;
- автоматическая классификация «производитель/оптовик/розница/подрядчик» определяется по основному ОКВЭД (`classify_okved`) и **с 26 августа выводится в интерфейсе** (бейдж у названия + фильтр «Производители»); ограничение в том, что она есть только у компаний с подтверждённой записью в реестре — на 26 августа это 115 профилей из 303;
- мобильный интерфейс требует отдельного регулярного визуального регрессионного прогона;
- в экране «Поставщики» нет импорта/экспорта CSV и ручного слияния дублей-карточек — осознанно отложено, см. раздел 7 [suppliers-screen.md](suppliers-screen.md).

### 16.0.1. Почему заявка 1056 зависала и как исправлено

До 27 августа поиск запускался в `supplier_app.py` через daemon-поток. Vercel
возвращает `202`, после чего может заморозить экземпляр функции; поток погибал
вместе с экземпляром, а новый старт помечал заявку ошибкой «Поиск прерван
перезапуском сервера». Именно это произошло с №1056: в продакшен-базе не было
ни результатов SERP, ни поставщиков, а в `request_meta` оставалась эта ошибка.

Теперь старт поиска только создаёт durable job в Postgres. API
`POST /api/requests/{id}/search/step` обрабатывает одну позицию или один сайт,
сохраняет курсор и выдаёт lease на 120 секунд. Если функция оборвалась,
следующий вызов забирает просроченный lease и продолжает с сохранённого места.
Один запрос к XMLRiver в serverless-шаге ограничен 12 секундами и двумя
попытками, чтобы не упираться в лимит функции 60 секунд; неудачная попытка
остаётся повторяемой.
Страница заявки вызывает этот endpoint каждые 1,5 секунды только пока статус
`searching`; после закрытия страницы работа ставится на паузу, но не теряется.
Это решение не добавляет новый платный сервис и не требует Vercel Cron, чей
минимальный интервал зависит от тарифа.

### Таблица сравнения коммерческих предложений (отложено 27 августа 2026)

**Задача.** Сейчас продукт доводит закупку до «письма ушли» и останавливается,
а работа снабженца там только начинается: сравнить предложения, выбрать,
обосновать выбор. Правая половина такой таблицы у нас уже есть (возраст,
выручка, прибыль, статус ЕГРЮЛ), не хватает левой — цены, срока и условий
оплаты из ответов.

**Предложенный порядок реализации:**

1. **Ручной ввод.** Рядом с ответом форма: цена, срок, условия оплаты,
   минимальная партия. Работает с любым форматом ответа — PDF, Excel,
   «звоните», — и никогда не врёт. Даёт главное: одну таблицу вместо десятка
   писем.
2. **Подсказка модели поверх формы.** Конвейер уже умеет вызывать LLM с
   бюджетом. Цена и срок извлекаются из тела письма и показываются **как
   предложение с подсветкой**, которое человек подтверждает. Цифра от модели не
   должна попадать в таблицу молча: ошибка в цене — это неверное решение о
   закупке на реальные деньги.
3. **Разбор вложений** (PDF/Excel) — отдельная работа, имеет смысл только
   после того, как шаги 1–2 начнут приносить пользу.

**Открытый вопрос, который нужно решить до реализации:** сравнивать по заявке
целиком или по каждой позиции отдельно. Если в заявке четыре позиции и
поставщик отвечает по двум, таблица «поставщик × позиция» честнее, но заметно
сложнее и в интерфейсе, и в модели данных.

### 26 августа 2026 года — ложный ИНН от веб-поиска

Владелец проекта заметил на заявке №1053, что `master-water.ru` показывает чужой

**Диагностика.** Живым запросом `WebLookup.find_inn("master-water.ru")`
воспроизведена именно та ошибка: сайт блокирует обход, поэтому сработал
резервный веб-поиск, а Rusprofile выдал карточку **другого** юрлица с тем же
названием — функция брала первый ИНН из сниппета каталога без проверки, что
сниппет вообще про этот сайт. Guard `registry_ownership_unknown()` не спасал:
у чужой записи в Checko просто нет сайта/почты, и «нечем опровергнуть»
трактовалось как «можно принять» — верно для ИНН с самой страницы сайта
(сильная улика), неверно для догадки по совпадению имени в чужом каталоге
(слабая). Отдельно всплыл более широкий баг в `_enrich_one`: даже когда запись
реестра отбраковывалась как «не та компания», сырой ИНН всё равно уходил в
`apply_supplier_enrichment()` и оседал в карточке — проверка блокировала имя и
телефон, но не сам номер. Подробности и код — [enrichment-and-cache.md](enrichment-and-cache.md) §2.1.

**Исправлено:**
- `InnHit.domain_confirmed` (`inn_extractor.py`) — новый флаг: правда ли домен
  сайта упомянут там, где найден ИНН, а не просто совпало название компании;
- `web_lookup.find_inn()` теперь ищет среди кандидатов подтверждённый домену
  вариант и явно помечает неподтверждённые;
- `_enrich_one`/`_enrich_registry_backlog` для неподтверждённого веб-хита требуют
  от Checko **положительного** совпадения домена, а не «не опровергнуто», и при

### Ограничения и решение по стоимости

Свободная глубина не отменяет ограничений внешнего поискового провайдера:
каждая дополнительная страница увеличивает количество запросов и время. В
продукте нет нового платного сервиса; точные текущие тарифы XMLRiver в этой
итерации не проверялись, поэтому бесплатность не заявляется. Значение `100`
является безопасным локальным верхним пределом, а не обещанием, что внешний
провайдер обработает такой запуск без квоты/таймаута.

Вложения шаблона сейчас передаются в JSON base64 и хранятся в БД; при массовой
рассылке существующий pipeline сохраняет отдельную копию вложения для каждого
письма. Для больших рабочих пространств следующий архитектурный шаг — object
storage с ссылкой/хешем и лимитами retention, но он в эту локальную итерацию не
включался.

## Исправление отображения времени писем — 28 августа 2026 года

- Время в базе и API хранится в UTC с явным смещением; браузер показывает его
  в локальном часовом поясе пользователя. На фактическом примере заявки №1055

  исходного письма, а не время получения текущего сообщения; его нельзя
  использовать для сортировки или подписи карточки.

  календарной дате в локальном часовом поясе, а не по пройденным 24 часам.
  Благодаря этому список и открытая переписка не расходятся около полуночи.
- Невалидная или пустая дата больше не превращается в некорректное время.
  Проверка выполнена на реальном рендере переписки с метаданными `07:30` и

- страница контактов Форнакс в локальном запросе вернула `403`, поэтому отсутствие результата не доказывает отсутствие email на сайте; адрес `zakaz@fornaks.ru` виден в индексированной поисковой выдаче, но это вторичный источник, а не прямое подтверждение страницы;
- URL контактов Камин.Клик вернул только короткий служебный ответ на 274 байта без контактного HTML, поэтому показанный на скриншоте `i168@yandex.ru` нельзя выдавать за результат автоматического извлечения из этой загрузки.

### Что изменено

- Добавлен осторожный repair-pass для одной запятой или точки с запятой перед TLD: `zakaz@company,ru` превращается в `zakaz@company.ru` только после повторной строгой проверки домена.
- Восстановленный адрес получает метод `*_repaired`, доказательство с исходной строкой и потолок `medium`: MX и совпадение домена не превращают исправленную опечатку в автоматически подтверждённую почту.
- Разбор `mailto:` больше не делит домен `company,ru` на два кандидата; при этом список нескольких адресов через `;` или `, name@...` продолжает разделяться.
- Нормализация учитывает полноширинные `＠`, `。`, `．` и пробелы вокруг `@`; JSON-поля email допускают запятую внутри значения.
- Web fallback больше не использует отдельную слабую регулярку: поисковый сниппет проходит через тот же extractor и сохраняет вторичный метод `web`/`web_repaired`.

### Проверка и границы

Офлайн-регрессии покрывают malformed `mailto`, JSON/атрибут, JavaScript, обычный адрес, отметку исправления, потолок доверия и fake web fallback. На реальных страницах повторно подтверждено: `donetsk.dongradus.ru` теперь восстанавливает кандидат, а `ermak-termo.com` извлекается при доступном HTML. `403`, `robots.txt`, 429 и короткий служебный ответ не обходятся — для них сохраняется статус ограничения и используется разрешённый secondary-source fallback.

Внешний платный XMLRiver-запрос в этой итерации не выполнялся; новые внешние сервисы и production/deployment не подключались. Следующий шаг — добавить сохранение причины недоступности и найденных secondary-source evidence в карточку поставщика, чтобы пользователь видел разницу между «не найдено» и «страница не была доступна».

## Историческая реализация — Iteration 1 outgoing mail integrity

Этот раздел является датированным дополнением к историческим записям выше.
Исходящая массовая почта теперь требует idempotency key. Fingerprint описывает
стабильный пользовательский payload, а не изменяемое enrichment-состояние;
фактический персонализированный текст фиксируется snapshot-ом в
`mail_send_operation_targets`. Получатели нормализуются, дедуплицируются и
хранятся там; операция проходит
`assembling` → `ready`, и только `ready`-задачи видны worker.

Для нового worker используется atomic claim с `claim_token`, владельцем и
lease. Перед контактом с провайдером в БД фиксируется `irreversible_at`; DB
транзакция не удерживается во время SMTP/IMAP. После SMTP success результат
фиксируется атомарно в job/message/request state, затем best-effort сохраняется
копия в «Отправленных». Сбой записи результата не вызывает обычный retry.
Timeout/disconnect после начала передачи переводит job в `delivery_unknown`;
это состояние не возвращается в очередь автоматически.

Проверка выполняется provider-neutral контрактом по постоянному RFC
`Message-ID`: `found` переводит письмо в `sent`, `not_found` и `unavailable`
оставляют `delivery_unknown`. Угаданная папка «Отправленные» считается
`unavailable`. Для неопределённого письма доступны повторная проверка, ручной
resend с новым сообщением/Message-ID после явного подтверждения и manual
resolution. Resolution хранится snapshot-строкой и блокирует удаление заявки
до явного закрытия; само значение доставки не изменяется и запись переживает
удаление заявки.

Runtime kill switch проверяется в общей точке обоих исходящих путей: queued
worker и синхронного ответа на непривязанное письмо. Incoming sync и dashboard
в эту итерацию не переделывались.

Lease recovery выполняется при старте очереди. Периодического recovery в живом
процессе нет: истёкшая `sending` job может оставаться в этом состоянии до
restart. Это текущий technical debt, а не обещание полноценного runtime
recovery.

Подробный change-set, crash matrix, контракт идемпотентности и фактические
результаты тестов находятся в `EMAIL_INTEGRITY_ITERATION1_REPORT.md`.

## Iteration 2 — pacing / provider protection / account budgets

Iteration 1 = integrity / duplicate safety. Iteration 2 = pacing / provider
protection / account budgets. Новая логика использует ту же цепочку
`MailService → MailRepository → mail_jobs → MailQueue → I1 guards → SMTP`.
Для каждого account persisted limiter атомарно резервирует slot, применяет
bounded jitter, rolling hour/day budgets, cooldown и circuit breaker. Ожидание
не увеличивает `attempts` и не создаёт audit spam; suppression проверяется
непосредственно перед отправкой.

Текущие conservative application defaults: `MAIL_PACING_MIN_SECONDS=30`,
`MAIL_PACING_MAX_SECONDS=60`, `MAIL_MAX_PER_HOUR=100` и
`MAIL_MAX_PER_DAY=100`. Это внутренние настройки SupplyDesk, а не официальный
безопасный лимит Yandex; они не гарантируют отсутствие блокировки, доставку или
попадание во «Входящие». Приблизительная математика: 30 секунд — до ~120/час,
45 секунд в среднем — около ~80/час, 60 секунд — около ~60/час; 100 писем —
примерно 50–100 минут до дополнительных cooldown/retry/budget/provider
задержек.

Реализация и ограничения описаны в `EMAIL_PACING_ITERATION2.md`, а фактические
проверки — в `EMAIL_PACING_ITERATION2_REPORT.md`. PostgreSQL в текущей среде не
запускался и не обозначается как проверенный.

### Health policy corrective pass — 2026-08-29

Первоначальная transient-политика использовала lifetime cumulative count
targets и могла навсегда удерживать campaign в `paused_for_health` после

## Campaign size / duration correction — 2026-08-29

Единый `MAIL_CAMPAIGN_MAX_RECIPIENTS` установлен в default `300`, с защитным
диапазоном `1..500`. Значение возвращается в preflight metadata и используется
одинаково в preflight, preview и queue validation; поэтому 301+ получает
`campaign_size_out_of_range`, а выбранные адреса не обрезаются автоматически.

Размер кампании не меняет account protection: pacing 30–60 секунд, лимит 100 в
час и rolling 24-hour budget 100 сохранены. Для 120 получателей duration API
возвращает `{minimum, average, maximum}` = `{3570, 5355, 7140}` секунд, а UI
показывает «около 1 ч 29 мин.» и диапазон вместо `NaN`. Если кампания больше
текущего дневного бюджета, интерфейс предупреждает о budget wait. Policy
warning ordinary Yandex сохранён; 300 — внутренний лимит SupplyDesk, не
обещание безопасной массовой рассылки или Inbox placement. Live SMTP не
вызывался, `outgoing_enabled=0`.

**Простыми словами:** можно выбрать до 300 поставщиков в одной кампании, но
почтовый ящик всё равно будет отправлять постепенно и не более 100 за текущее
24-часовое окно. Список свыше 300 не будет обрезан незаметно, а оценка времени
теперь показывается обычными часами и минутами.
