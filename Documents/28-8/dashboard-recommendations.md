## 1. Назначение dashboard

Supplydesk — рабочий инструмент снабженца. Dashboard должен отвечать на три вопроса:

1. Что прямо сейчас требует моего действия?
2. На каком этапе находятся мои закупки?
3. Какое следующее действие я могу выполнить?

Основной пользовательский сценарий проекта:

```text
Заявка → отдельные позиции → поиск поставщиков → проверка → подготовка писем → очередь → переписка
```

Поэтому dashboard должен быть рабочей панелью процесса, а не набором декоративных графиков.

## 2. Текущее содержимое

Сейчас на dashboard есть:

- KPI «Активные заявки»;
- KPI «В поиске»;
- KPI «Новые ответы»;
- KPI «Требует внимания»;
- список последних заявок;
- статус заявки;
- количество найденных поставщиков;
- количество ответов;
- основная кнопка «Новая заявка»; ручная кнопка обновления не нужна — пользователь может обновить страницу через `F5`.

Текущая реализация уже даёт понятную desktop-иерархию: заголовок → KPI → список заявок. Основной недостаток — экран показывает счётчики, но недостаточно хорошо объясняет, что именно делать дальше.

## 4. Приоритетные улучшения

### 4.1. Блок «Требуют действия» — приоритет P1

На главном экране нужен не только числовой KPI, но и список конкретных проблем.

В блок могут попадать:

- заявка завершилась со статусом «Ошибка»;
- поиск долго остаётся в одном состоянии;
- письмо не отправилось или попало в failed;
- обнаружен жёсткий bounce;
- появился новый непрочитанный ответ;
- не подключена рабочая почта;
- поставщик найден, но контакт не подтверждён;
- приближается или уже прошёл дедлайн заявки.

Каждый элемент должен содержать:

- название заявки или поставщика;
- понятную причину;
- время последнего изменения;
- одно основное действие.

Примеры действий:

- «Открыть заявку»;
- «Повторить поиск»;
- «Открыть переписку»;
- «Проверить поставщика»;
- «Подключить почту».

Критерии готовности:

- пользователь видит не только число проблем, но и сами проблемы;
- каждая проблема ведёт в правильный раздел;
- у ошибки есть понятное восстановление;
- список не смешивает ошибки поиска, письма и входящих сообщений без указания причины.

### 4.2. Согласовать KPI «Требует внимания» — приоритет P1

Нужно определить единый контракт KPI.

Рекомендуемая версия:

```text
Требует внимания = ошибки заявок
                    + ошибки отправки писем
                    + зависшие процессы
                    + просроченные дедлайны
```

Непрочитанные ответы лучше оставить отдельным KPI «Новые ответы», чтобы одна проблема не считалась дважды.

Если бизнес хочет считать только ошибки отправки, KPI следует переименовать в «Ошибки отправки». Название «Требует внимания» слишком широкое для одного SQL-фильтра по `mail_jobs`.

Критерии готовности:

- заявка со статусом «Ошибка» влияет на KPI;
- failed mail job влияет на KPI;
- зависший поиск имеет понятное правило определения;
- ссылка KPI ведёт в список именно тех сущностей, которые посчитаны;
- нулевое значение не скрывает существующую ошибку.

### 4.3. Полноценный error-state и retry — приоритет P1

Сбой `/api/dashboard/summary` не должен превращать экран в dashboard с нулевыми значениями.

Нужны состояния:

```text
loading → loaded
       ↘ error → retry
```

В error-state показать:

- заголовок «Не удалось загрузить dashboard»;
- короткое объяснение без технического стектрейса;
- кнопку «Повторить»;
- сохранённый layout страницы или контекст последней успешной загрузки, если он есть.

Критерии готовности:

- ошибка не отображается как нулевые KPI;
- в консоли нет необработанного rejection;
- retry повторяет только нужный запрос;
- во время retry кнопка блокируется и показывает состояние загрузки;
- после успешного retry данные возвращаются без перезагрузки страницы.

### 4.4. Ссылка «Все заявки» — приоритет P1/P2

Dashboard может показывать последние 8 заявок, но это должно быть явно обозначено.

Рекомендуемый вариант:

- заголовок «Мои заявки»;
- справа ссылка «Все заявки»;
- подзаголовок «Последние 8 заявок».

Если список станет большим, ограничение и сортировку лучше выполнять на backend. Не следует отдавать весь архив только для того, чтобы frontend показал первые 8 строк.

Критерии готовности:

- пользователь понимает, что список сокращён;
- доступен полный список без обходных путей через sidebar;
- сортировка последних заявок остаётся стабильной;
- пустое состояние не ломает кнопку «Все заявки».

## 5. Состав целевого dashboard

### 5.1. Верхняя панель

В верхней части оставить:

- заголовок «Дашборд»;
- короткое описание назначения экрана;
- основную кнопку «Новая заявка»;
- время последнего успешного обновления.

Отдельную кнопку «Обновить» не показывать: обычное обновление выполняется через `F5`. Кнопка «Повторить» допустима только внутри error-state и должна повторять конкретный неудачный запрос.

На mobile действия должны быть компактными и не создавать пустую широкую оболочку вокруг маленькой кнопки.

### 5.2. KPI первого уровня

Рекомендуемые KPI:

1. Активные заявки.
2. В поиске.
3. Новые ответы.
4. Требует внимания.

Для каждого KPI должны быть определены:

- источник данных;
- период или момент измерения;
- фильтр при переходе;
- поведение при нуле;
- правила цветового выделения.

Не следует делать все карточки яркими одновременно. Цвет должен показывать действие или проблему.

### 5.3. Состояние конвейера закупки

Добавить компактный блок с этапами:

```text
Заявки → Поиск → Поставщики → Письма → Ответы
```

Для каждого этапа можно показывать количество, но только если число имеет однозначный смысл.

Полезные показатели:

- сколько заявок активно;
- сколько сейчас ищется;
- сколько поставщиков найдено;
- сколько писем отправлено;
- сколько ответов получено;
- где есть ошибка или остановка.

Для активной заявки желательно показывать прогресс и текущую стадию, а не только общий статус.

### 5.4. Блок «Мои заявки»

В desktop допустима таблица с колонками:

- заявка;
- статус;
- поставщики;
- ответы;
- обновлено или дедлайн.

В mobile использовать карточку заявки:

```text
Кабель ВВГ
Поиск завершён · 79 поставщиков · 12 ответов
Обновлено 5 минут назад                         Открыть
```

Статус, количество ответов и проблемный признак должны быть видны без горизонтальной прокрутки.

Ошибочные и активные заявки желательно поднимать выше завершённых.

### 5.5. Блок «Последняя активность»

Показывать короткую ленту событий:

- поиск завершён;
- найден новый поставщик;
- получен ответ;
- письмо не доставлено;
- поставщик добавлен в чёрный список;
- данные компании обновлены.

Каждое событие должно иметь время и ссылку на объект.

Лента не должна превращаться в полноценный журнал аудита. Её задача — восстановить контекст после возвращения пользователя в систему.

### 5.6. Состояние почты

Так как рабочая почта участвует в отправке и получении сообщений, на dashboard полезно показывать:

- почта подключена или нет;
- адрес подключённого ящика;
- время последней синхронизации;
- наличие ошибки синхронизации;
- действие «Проверить почту» или «Подключить почту».

Не нужно показывать технические OAuth-параметры или токены.

### 5.7. Пустое состояние

Если заявок нет, показать:

- что сейчас пусто;
- зачем нужна заявка;
- кнопку «Создать первую заявку»;
- при необходимости — «Подключить Яндекс.Почту».

Демонстрационные данные должны быть явно обозначены как демонстрационные и не должны выглядеть как реальные заявки пользователя.

## 6. Быстрые действия

Минимальный набор:

- создать новую заявку;
- открыть все заявки;
- открыть новые ответы;
- повторить ошибочный поиск;
- проверить или подключить почту.

Действия должны зависеть от состояния. Не показывать кнопку, которая в текущем состоянии ничего не делает.

## 7. Доступность и взаимодействие

Для dashboard обязательно проверить:

- видимый focus у ссылок и кнопок;
- достаточную область нажатия у мобильных действий;
- доступные имена иконок и кнопок;
- правильную семантику таблицы и `scope="col"` у заголовков;
- возможность открыть заявку с клавиатуры;
- отсутствие зависимости только от цвета статуса;
- понятный результат после `F5` и retry;
- корректное поведение меню на mobile, включая Escape и возврат фокуса.

Строка таблицы не должна выглядеть кликабельной, если она не доступна с клавиатуры. Предпочтительно иметь явную ссылку на заявку.

## 8. Визуальное направление

Нужно придерживаться решений из [DESIGN.md](DESIGN.md):

- спокойный холодный фон;
- graphite navigation rail;
- cobalt для действий и focus;
- Procure Sans для заголовков и UI-копирайта;
- белые поверхности только для рабочих областей;
- сдержанные тени;
- цвет только для состояния или приоритета;
- контентные строки должны определять высоту, а не жёсткая сетка.

Нужно избегать:

- контейнера вокруг каждого текста;
- лишних градиентов и декоративных бейджей;
- одинаково ярких карточек;
- BI-графиков без решения, которое они помогают принять;
- визуального копирования типового admin-шаблона.

У Supplydesk должна появиться собственная узнаваемость через рабочий процесс: этапы закупки, состояние поиска, качество контактов и ответы поставщиков.

## 9. Что не добавлять на главный экран

Не добавлять без отдельной бизнес-задачи:

- финансовые графики ради визуального наполнения;
- диаграммы, которые не ведут к действию;
- подробные карточки каждого поставщика;
- полную историю почты;
- технические расходы XMLRiver, LLM и Checko для обычного снабженца;
- дублирование функций экранов «Поставщики», «Переписка» и «Настройки».

Расходы, лимиты и техническое состояние внешних сервисов можно вынести в отдельный операционный или административный экран.

```text

                                Обновлено 14:32

[Активные] [В поиске] [Новые ответы] [Требуют внимания]
```

Порядок важен: сначала действие, затем состояние процесса, затем список и история.

На mobile:

```text
Дашборд                         [Новая заявка]
[KPI 1] [KPI 2]
[KPI 3] [KPI 4]

Требуют действия
Карточка проблемы

Мои заявки
Карточка заявки
```

## 12. Definition of Done

Dashboard можно считать готовым после выполнения условий:

- ошибки заявок не скрываются за нулевым KPI, а KPI ведёт в совпадающий фильтр;
- API failure показывает понятный error-state;
- retry работает и не создаёт необработанных console errors;
- полный список заявок доступен явно;
- mobile не требует горизонтального скролла для статуса и ключевых счётчиков;
- нет page-level overflow на desktop, tablet и mobile;
- все действия доступны с клавиатуры;
- loading, empty, error, success и permission-state имеют понятное сообщение;
- визуальное направление соответствует `DESIGN.md`;
- проверены screenshots на `1920×1080`, `1440×900`, `1280×800`, `1024×768`, `768×1024` и `390×844`;
- проходят typecheck, lint, build и релевантные backend/frontend smoke-тесты.

## 13. Открытые продуктовые решения

Перед реализацией блока «Требуют действия» нужно зафиксировать:

1. Считать ли просроченный дедлайн проблемой автоматически.
2. Через какое время без прогресса заявка считается зависшей.
3. Должен ли bounce попадать в общий KPI или только в экран поставщика.
4. Показывать ли техническую стоимость поиска обычному пользователю.
5. Какой период использовать для response rate и средней скорости ответа.

До принятия этих решений не следует добавлять новые KPI только ради визуального заполнения dashboard.

## 14. Аккордеон непривязанных входящих писем — 27 августа 2026

Для блока «Письма без привязки к заявке» выбран паттерн раскрываемого списка:

- дашборд показывает только три самых новых доступных письма из preview;
- все три карточки после загрузки закрыты; каждую можно раскрыть независимо,
  в том числе открыть все три одновременно;
- тело письма загружается только для раскрытого элемента через существующий
  `GET /api/mail/inbox/conversation`;
- чтение на дашборде не меняет статус письма и не уменьшает `unmatched_mail`;
  amber-индикатор «Непрочитанное письмо без привязки» остаётся видимым;
- при ошибке загрузки отдельное письмо показывает локальный retry, не ломая весь
  дашборд;
- ссылка «Открыть в переписке» сохранена для ручной привязки к заявке.

Это сохраняет баланс между быстрым обзором последних входящих и возможностью
прочитать любое письмо прямо на главной странице без ложного изменения статуса.
