# Парсер поисковой выдачи (шаг 1 PoC)

> Полная документация текущего проекта Supplydesk: [PROJECT_DOCUMENTATION.md](PROJECT_DOCUMENTATION.md). В ней описаны личный кабинет, заявки, позиции, поиск поставщиков, API, база данных, почта, Vercel и тестирование.

Берёт ключ → добавляет коммерческий маркер «купить» → прогоняет через
[XMLRiver](https://xmlriver.com) на заданную глубину страниц → отдаёт список сайтов.

Это первый кирпич конвейера PoC из бэклога (Эпик 1, Test 1.1): собрать сырую
выдачу, чтобы потом мерить долю мусора и проверять извлечение контактов.
Фильтрации «поставщик / не поставщик» здесь **нет** — парсер отдаёт ровно то,
что показал поисковик.

```
кирпич  ──►  «кирпич купить»  ──►  XMLRiver (N страниц)  ──►  CSV со списком сайтов
```

## Установка

```bash
pip install -r requirements.txt
```

Скопировать `.env.example` в `.env` и вписать доступы из
[личного кабинета XMLRiver](https://xmlriver.com/account/):

```
XMLRIVER_USER=12345
XMLRIVER_KEY=abcdef...
```

Вместо `.env` можно передавать `--user` и `--key` аргументами.

## Использование

```bash
python serp_parser.py "кирпич" --pages 3
```

Глубина задаётся на входе — `--pages`. Разницу в нумерации страниц
(Яндекс считает с 0, Google с 1) парсер закрывает сам.

Пакетный прогон по файлу с ключами, Google, Москва:

```bash
python serp_parser.py --file keywords.txt --pages 5 --engine google --loc 1000028 --out results/msk.csv
```

Посмотреть, какие запросы уйдут, не тратя лимиты (ключ не нужен):

```bash
python serp_parser.py "кирпич" --pages 3 --dry-run
```

Баланс и стоимость тысячи запросов — для расчёта unit-экономики (Test 3.1):

```bash
python serp_parser.py --balance
```

## Ключевые параметры

| Параметр | Что делает |
|---|---|
| `--pages N` | глубина: сколько страниц выдачи забрать по каждому ключу |
| `--engine yandex\|google` | поисковик (по умолчанию `yandex`) |
| `--suffix СЛОВО` | другой маркер вместо «купить» (`--no-suffix` — искать чистый ключ) |
| `--file ФАЙЛ` | список ключей, по одному на строку |
| `--lr` / `--loc` / `--country` / `--domain` / `--device` | геопривязка и устройство |
| `--param имя=значение` | любой другой параметр API, можно повторять |
| `--dedup root\|host\|url\|none` | как схлопывать дубли (`root` склеивает `spb.metall.ru` и `msk.metall.ru`) |
| `--exclude-file ФАЙЛ` | стоп-домены (агрегаторы, инфо-порталы) |
| `--keep-going` | не прекращать обход после первой пустой страницы |
| `--out` / `--json` | куда сохранить результат |
| `--delay` / `--timeout` / `--retries` | темп запросов и устойчивость |

Полный список: `python serp_parser.py --help`

## Результат

CSV с разделителем `;` в кодировке UTF-8 с BOM (Excel открывает без плясок).
Колонки:

`keyword` · `query` · `engine` · `page` · `position` · `url` · `host` ·
`root_domain` · `title` · `snippet` · `found_total` · `collected_at`

`position` — сквозная позиция сайта по ключу с учётом всей глубины;
`found_total` — сколько всего документов нашёл поисковик по запросу.

## Устойчивость

XMLRiver штатно отдаёт временные ошибки — занятые каналы сбора (110, 111),
сетевые сбои (500, до 20% ответов по документации — это норма), просьбу
подождать (203). Клиент их ретраит с экспоненциальной паузой и джиттером,
код 203 читает задержку прямо из текста ответа.

Фатальные ошибки — нулевой баланс (200), битый ключ (42), запрет по IP (45),
неверные параметры — не ретраятся, а сразу выводятся понятным текстом.
Код 15 («ничего не найдено») не ошибка, а пустая выдача.

Упавшая страница не роняет весь прогон: она пропускается, счётчик ошибок
попадает в итоговую статистику.

# Шаг 2. Сбор email с сайтов

```
список сайтов ──► обход контактных страниц ──► email с оценкой достоверности
```

```bash
python collect_contacts.py --from-serp results/кирпич_yandex_20260820.csv
```

## Про точность

Точность здесь — два разных числа, и путать их нельзя:

- **Полнота при условии, что адрес опубликован.** Замер на живой выдаче по «кирпич»:
  **19 из 20 открывшихся сайтов** (95%). Единственный промах — сайт без страницы контактов.
- **Достоверность выданного.** Всё, что не подтверждено строгими проверками, не
  выбрасывается, а уходит в блок «Возможные — требуется проверка», как и записано
  в утверждённых требованиях.

Откуда взялись адреса на живой выдаче: `mailto` — 68, JSON-поля внутри
скриптов — 47, текст и микроразметка — остальное.

## Способы извлечения

| Способ | Что ловит |
|---|---|
| `mailto` | ссылка `mailto:` — адрес указан явно |
| `jsonld` / `microdata` | разметка schema.org |
| `jsonfield` | поле `"email"` в JSON внутри скриптов — так отдают контакты филиалов и менеджеров |
| `cfemail` | защита Cloudflare `data-cfemail`, расшифровывается |
| `text` | видимый текст страницы |
| `script` | адрес в коде скрипта, в том числе склеенный из кусков |
| `obfuscated` | `info (собака) site точка ru` и подобное |

## Барьеры точности

- **MX-запись домена.** Если домен не принимает почту — адрес не подтверждается.
  Ловит выдуманное и опечатки, но проверяет только доменную половину адреса.
- **Отсев мусора.** Имена файлов (`logo@2x.png`), шаблонная рыба (`name@domain.ru`),
  дефолты Битрикса (`sale@site.ru`), адреса CMS и веб-студий из подвала, хеши трекеров.
- **Потолки достоверности.** Технический адрес (`noreply@`) не подтверждается никогда —
  письмо туда не дойдёт. Восстановленный из обфускации — тоже: MX подтверждает домен,
  а рискует локальная часть.
- **Расхождение ссылки и текста.** Реальный случай с `kirpich-ko.ru`:
  `<a href="mailto:buh@gidra360.ru">buh-baza@mail.ru</a>` — показан один адрес,
  ссылка ведёт в другую компанию. Такое помечается и не подтверждается.

## Где полнота упирается в потолок

| Причина | Чинится? |
|---|---|
| Сайт не отвечает (`n-dom.com`, `kirpi4nik.com` молчат и 45 секунд) | нет, сайт мёртв |
| Антибот маркетплейса (`wildberries.ru` отдаёт 498 при любом UA) | нет, и в списке поставщиков ему не место |
| `robots.txt` запрещает обход | решение бизнеса, ключ `--ignore-robots` |
| Контакты рисуются JavaScript'ом | нужен рендеринг страницы |
| Адрес нарисован картинкой | нужен OCR |
| Только форма обратной связи | недостижимо в принципе |

Причина попадает в колонку `no_email_reason` — видно, что чинить, а что нет.

## Параметры шага 2

| Параметр | Что делает |
|---|---|
| `--from-serp CSV` | взять домены из выгрузки шага 1 |
| `--max-pages N` | сколько страниц смотреть на сайте (по умолчанию 6) |
| `--workers N` | сколько сайтов обходить параллельно |
| `--no-mx` | не проверять MX — быстрее, но достоверность ниже |
| `--ignore-robots` | игнорировать `robots.txt` (по умолчанию соблюдается) |
| `--limit N` | взять только первые N доменов |

# Шаг 3. Сбор ИНН

```bash
python collect_inn.py --from-serp results/кирпич_yandex_20260820.csv
```

## Почему здесь возможна настоящая точность

У ИНН есть контрольная сумма — номер проверяется арифметически, никуда не
обращаясь. Она надёжно ловит опечатки, но её силу легко переоценить: у
10-значного ИНН контрольная цифра одна, поэтому **каждое десятое случайное
число её проходит** (у 12-значного цифры две — каждое сотое). Замерено в
`test_inn.py`.

Отсюда правило: для номера, предложенного моделью, контрольной суммы
**недостаточно**. Решающая проверка — реестр DaData: он подтверждает, что за
номером стоит существующая компания, и называет её. Без реестра ИНН не
поднимается выше «вероятен» ни при каком источнике.

Замер на живой выдаче по «кирпич»: **ИНН найден на 16 из 20 открывшихся сайтов (80%)**,
все — по явной подписи «ИНН ...».

## Лестница ступеней

| Ступень | Что делает | Цена |
|---|---|---|
| 1 | разметка schema.org, подписанный «ИНН 7701234567» | бесплатно |
| 2 | числа без подписи, отсеянные контрольной суммой | бесплатно |
| 3 | языковая модель по тексту страницы (`--llm`) | платно |
| 4 | подтверждение в реестре DaData | бесплатно до 10 000 запросов в день |

Каждая следующая включается только там, где предыдущая вернула пусто.

## Роль языковой модели

Модель **не источник истины**. Она предлагает кандидата, а решают контрольная
сумма и реестр — те же проверки, что и для найденного регуляркой. Выдуманный
номер не пройдёт арифметику, чужой не подтвердится в реестре. Поэтому ступень 3
поднимает полноту и не может уронить точность.

Где модель бесполезна: там, где HTML не получен (сайт не отвечает, `robots.txt`,
антибот). Нечего показать — нечего и разбирать.

```bash
python collect_inn.py --from-serp results/serp.csv --llm --llm-model claude-haiku-4-5
```

Ключ `--llm-limit` ограничивает число вызовов за прогон — защита от неожиданного счёта.

## Где искать реквизиты

Ключевая находка замера: ИНН чаще лежит не в «Контактах», а в **публичной оферте
и политике обработки персональных данных** — там он обязателен по закону. Добавление
этих страниц в обход подняло полноту с 70% до 80% бесплатно, без всякой модели.

## Ловушка кириллицы

«ИНН» как подстрока сидит внутри обычных русских слов: кам**инн**ые топки,
дл**инн**ого формата, подл**инн**ость. Без границы слова в регулярке любое число
после них читается как ИНН. На сайтах кирпича такие слова встречаются на каждой
странице — проверка на это есть в `test_inn.py`.

# Поиск в интернете и верификация

## Когда обойти сайт нельзя

Часть сайтов недостижима: не отвечает, закрыта `robots.txt` или антиботом.
Модель тут бессильна — показать ей нечего. Но сведения о компании в интернете
есть, и берутся они тем же XMLRiver, который уже подключён на шаге 1.

```bash
python collect_contacts.py --from-serp results/serp.csv --web --verify
python collect_inn.py --from-serp results/serp.csv --web
```

Замер: **email нашёлся для всех 27 сайтов** против 19 без этой ступени.
Закрытые `robots.txt` `gkz.ru` и `rf.petrovich.ru` дали адреса на собственных
доменах, мёртвый `n-dom.com` — тоже. Цена: 2 запроса XMLRiver на сайт, 5 копеек.

Почему не поисковая модель (Perplexity Sonar и подобные): XMLRiver стоит
2,5 копейки за запрос и ищет в Яндексе, Sonar — около 17 копеек и ищет в
западном индексе. Для российских поставщиков Яндекс точнее и в семь раз дешевле.
Разделение обязанностей: **XMLRiver ищет, регулярка забирает очевидное из
сниппетов, модель подключается только к остатку**.

## Верификация

Одиночный признак ничего не доказывает — доказывает совпадение независимых
источников. Модуль `verify.py` сводит проверки в вердикт.

**Email:**

| Проверка | Что доказывает |
|---|---|
| Синтаксис | ничего, только отсеивает мусор |
| MX-запись домена | домен принимает почту; про локальную часть молчит |
| Домен адреса = домен сайта | принадлежность компании |
| Найден и на сайте, и в выдаче | самое сильное: независимые источники не ошибаются одинаково |
| Ответ почтового сервера (`smtp_probe`) | ненадёжно, по умолчанию выключено |

Подтверждаем при MX **плюс** доказанной принадлежности — своим доменом либо
вторым источником. Одного MX мало: он про домен, а не про адрес.

**ИНН:**

| Проверка | Что доказывает |
|---|---|
| Контрольная сумма | ловит опечатки; каждое десятое случайное 10-значное число её проходит |
| Реестр DaData | компания существует. Решающая проверка |
| Название из реестра ≈ название сайта или домен | что ИНН принадлежит **владельцу сайта** |
| Повтор на нескольких страницах | устойчивость находки |

Третья проверка самая недооценённая. На странице реквизитов рядом с ИНН фирмы
стоит ИНН её банка — без сверки названия в чёрный список попадёт Сбербанк.
Сравнение идёт по значимым словам с транслитерацией: «ООО "БРАЕР"» ↔ `braer.ru`,
«ООО "Кирпич"» ↔ `kirpich.ru`.

## Выбор модели

Вопрос «какая модель нужна» решается замером, а не мнением. Есть 16 сайтов, где
ИНН найден детерминированно — готовый эталон:

```bash
python benchmark_models.py --prepare --from-serp results/serp.csv
python benchmark_models.py --run
```

Стенд кэширует страницы на диск, прогоняет кандидатов по одним и тем же данным
и печатает точность и рубли за 1000 сайтов. Модели даётся ровно та страница, из
которой регулярка достала эталон, — иначе меряется не умение читать, а везение
с выбором страницы.

Модели подключены через [RouterAI](https://routerai.ru) — OpenAI-совместимый
шлюз с оплатой в рублях, 458 моделей. Ключ в `.env` как `ROUTERAI_KEY`.

## Чего парсер намеренно не делает

Это по-прежнему открытые вопросы PoC, а не забытые фичи:

- не определяет регион и тип компании (производитель/дилер) — это Test 1.4;
- не решает, поставщик перед ним или инфо-портал, — критерии ещё не утверждены (Test 1.1);
- не определяет правила остановки поиска — в требованиях прямо отложено «до PoC»;
- не ходит в несколько потоков: XMLRiver блокирует на 10 минут за избыточную
  параллельность (код 115), поэтому темп задаётся `--delay`.

## Личный кабинет и отправка почты

Статический экран `supplier_finder.html` теперь обслуживается сервером `supplier_app.py`.
Он добавляет локальную сессионную авторизацию, SQLite, подключение Yandex Mail через
OAuth/XOAUTH2, шифрование токенов и очередь исходящих писем.

```powershell
python -m pip install -r requirements.txt
Copy-Item .env.example .env
python supplier_app.py
```

После запуска откройте `http://127.0.0.1:8000/supplier_finder.html`.
Полная настройка OAuth, ENV и тестовой отправки описана в
[`docs/mail-integration.md`](docs/mail-integration.md).
