## Цель и границы

Проверить, соответствует ли список переписки рабочему сценарию закупщика:
быстро понять, по каким заявкам пришёл ответ, что требует внимания и что
действительно было отправлено.

Не менялись application code, API, база, миграции, SMTP/IMAP и настройки
production. Проверка проводилась на текущем локальном runtime и read-only
срезе SQLite.

## Короткий вывод

**CONFIRMED:** сама идея «по заявкам» плюс отдельная вкладка «Без привязки»
правильная для продукта. Закупщик мыслит заявкой, а не плоским почтовым

отправлены, но они выглядят в списке как обычная переписка. В текущем срезе

**PARTIALLY CONFIRMED:** для обычных автоматически связанных входящих писем

и письмо во вкладке «Без привязки» не имеют такого же read/unread-контракта.
Живой unread-пример в текущей базе отсутствует: 16 входящих сообщений уже
прочитаны, `inbound_unread = 0`.

## Приоритетные изъяны

### P1 — queue-only письма попадают в «Переписку»

**FACT:** текущий read-only срез содержит:

- 63 outbound `sent`;
- 84 outbound `queued`;
- 2 outbound `failed`;
- 1 outbound `delivery_unknown`;
- 16 inbound `received`;
- 144 request-треда;
- 84 треда только со статусом `queued`.

`mail/repository.py:list_threads()` объединяет все строки `mail_threads` без
условия по статусу исходящих сообщений. В открытом треде
`1059:2907` пользователь видит «Вы · в очереди», но этот тред уже занимает
место в «Переписке».

**Влияние:** список создаёт ложное ощущение, что поставщику уже писали;
масштаб списка раздувается; сортировка по `last_message_at` смешивает историю
реальной переписки с транспортной очередью.

**Рекомендуемый контракт:**

- показывать тред в «Переписке», если есть входящее сообщение или исходящее
  `sent`, `failed`, `delivery_unknown`;
- queue-only `queued`/`sending` вынести в «Отправку/Очередь» внутри заявки или
  campaign monitor;
- `failed` и `delivery_unknown` не скрывать: это операционные состояния,
  требующие действия;
- если в уже существующем треде есть и `sent`, и новое `queued`, сам тред
  остаётся видимым, но строка должна показывать оба состояния явно.

### P1 — unread-контракт не покрывает manual-linked письма

**FACT:** обычный request-тред считает входящие без записи в
`mail_message_reads` как непрочитанные. `ThreadDetail` вызывает `onRead` после
загрузки такого треда. Но в UNION для manual-linked письма возвращается
`0 AS unread_count`; исходная запись остаётся в `mail_inbox_messages`, а
`inbox_conversation()` только читает её и ответы, без отметки прочтения.

**Влияние:** новое письмо, которое человек вручную привязал к заявке, может
попасть в «По заявкам» без индикатора нового ответа. Письма во вкладке «Без
привязки» вообще не имеют read/unread-поля и не выделяются как новые.

**Рекомендуемый контракт:** любое входящее письмо, принятое системой,
остаётся непрочитанным до открытия; ручная привязка меняет только связь с
заявкой, но не сбрасывает unread; открытие request-треда помечает входящие
этого треда прочитанными. Для manual/inbox нужен отдельный read-модельный
слой или единый способ материализации сообщения.

### P2 — статус не виден в строке списка

**FACT:** строка показывает только отправителя, дату, тему, `N писем` и
`N ответов`. Для понимания, что происходит, нужно открыть тред. В деталях
статус `в очереди` отображается серым текстом и визуально близок к обычному
`отправлено`.

**Рекомендация:** добавить компактный текстовый статус в строку: `Новый
ответ`, `Отправлено`, `В очереди`, `Ошибка отправки`, `Доставка не
подтверждена`. Не полагаться только на зелёную точку; для unread дать
доступный текст/`aria-label`, а не только `title` у пустого `span`.

### P2 — все группы раскрыты, хотя комментарий обещает обратное

**FACT:** `ThreadList.tsx` описывает стратегию «группа с непрочитанными
ответами раскрыта, остальные свёрнуты», но состояние `collapsed` создаётся как
`new Set()`. В live UI группа «Печь-камин — глубокий поиск 20» показывает
`131` тред и раскрыта по умолчанию.

**Рекомендация:** по умолчанию раскрывать только группы с новым ответом,
ошибкой доставки или активной отправкой; остальные показывать как компактные
строки-заголовки. При поиске раскрывать совпадения, как сейчас.

### P2 — off-canvas EmptyState на tablet/mobile

**FACT:** DOM-замер показал видимые элементы EmptyState за правой границей:

- `390x844`: элементы с `right=499`, при `clientWidth=380`;
- `360x800`: элементы с `right=469`, при `clientWidth=350`;
- `1024x768`: элементы с `right=1143`, при `clientWidth=1024`.

`scrollWidth` остаётся равен `clientWidth`, потому что родитель клиппит
содержимое через `overflow-hidden`; обычный smoke по горизонтальному scroll
этот дефект не обнаруживает.

**Рекомендация:** когда список активен, не рендерить EmptyState в соседней
flex-колонке; на narrow layout переключать list/detail взаимоисключающе.
После исправления повторить geometry audit на 390, 360 и 1024 px.

### P2 — «Ответить» доступен из queue-only треда

**FACT:** в queue-only треде `1059:2907` видны верхняя и нижняя кнопки
`Ответить`, хотя исходное письмо имеет статус `в очереди`.

**Рекомендация:** скрывать или менять первичное действие для queue-only на
`Ожидает отправки`; для `failed` и `delivery_unknown` сначала показывать
действие восстановления. Возможность написать новое письмо можно оставить
только как осознанное вторичное действие.

## Решение по результату

`FAIL` для текущего информационного контракта: P1-дефект с queue-only
тредами подтверждён. Архитектурное направление хорошее, но перед
дальнейшей полировкой нужно исправить границу между «перепиской» и
«очередью отправки», затем довести unread-модель до всех типов входящих.

Уровень уверенности: `HIGH` для queue-only и responsive findings;
`MEDIUM` для unread manual-linked gap до появления отдельного live unread
fixture.
